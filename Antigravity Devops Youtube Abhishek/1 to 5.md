# 📘 Day 1: Fundamentals of DevOps

**Goal:** Understand the "What" and "Why" of DevOps before learning any tools.

---

## 🤔 What is DevOps?

### Simple Definition
> DevOps is a **culture or practice** adopted by an organization to improve its ability to **deliver applications faster and more reliably**.

### Interview-Ready Definition
> *"DevOps is a process of improving application delivery by ensuring proper automation, maintaining quality, and implementing continuous monitoring and testing."*

### Real-World Example
| Without DevOps | With DevOps |
|---|---|
| A bug fix takes **10–30 days** to reach users | Bug fix reaches users in **hours or minutes** |
| Manual hand-offs between siloed teams | Automated pipelines handle everything |
| Slow, inconsistent deployments | Fast, repeatable, reliable releases |

> 🎮 Think of Android pushing an urgent security patch overnight — **that's DevOps.**

---

## 🏛️ The 4 Pillars of DevOps

> ⚠️ **Memorize these.** Every DevOps interview question leads back to these 4 pillars.

```
╔══════════════════════════════════════════════╗
║          4 PILLARS OF DEVOPS                 ║
╠══════════════════════════════════════════════╣
║  🤖 Automation  → Remove all manual steps   ║
║  ✅ Quality     → App works before shipping ║
║  📊 Monitoring  → Detect issues proactively ║
║  🧪 Testing     → Validate at every stage   ║
╚══════════════════════════════════════════════╝
```

| Pillar | What It Means | Why It Matters |
|--------|--------------|----------------|
| 🤖 **Automation** | Replace manual tasks with scripts/tools | Manual = slow and error-prone |
| ✅ **Quality** | App must meet standards before delivery | Fast delivery is useless if it's broken |
| 📊 **Monitoring** | Watch systems 24/7 for issues | You can't fix what you can't see |
| 🧪 **Testing** | Automated tests at every stage | Catch bugs before they reach users |

> 📝 **Note:** Monitoring and Observability are the same concept — use either in interviews.

---

## ⏳ Why DevOps? (The Evolution Story)

### ❌ Before DevOps
```
Developer → [SVN / Code Repo] → System Admin → Build & Release Eng → Tester → Production
```

| Old Role | What They Did |
|---|---|
| **System Administrator** | Created & managed servers (VMware, OpenStack, bare metal) |
| **Build & Release Engineer** | Packaged and deployed app to server |
| **Server Administrator** | Set up the application server (Tomcat, Apache) |
| **Tester** | Manually tested the app on each environment |

**Problems:** ❌ 100% manual | ❌ Siloed teams | ❌ Weeks to deploy | ❌ No consistency

### ✅ After DevOps
- One unified culture | Automated pipelines | Delivery in hours | Continuous feedback

> 💬 **Why is DevOps called a "culture"?** Because it requires people to continuously adapt and adopt better practices. A tool can be installed — culture must be built.

---

## 🎤 How to Introduce Yourself in a DevOps Interview

### ✅ 4-Step Framework
```
Step 1 → Current Role + Years of Experience
Step 2 → Previous Background (your bridge into DevOps)
Step 3 → Key Responsibilities (use the 4 pillars!)
Step 4 → Tools & Technologies (only what you actually know)
```

### 📝 Script — Experienced
> *"I'm a DevOps Engineer with 4–5 years of experience. Before this, I worked as a System Administrator. In my current role I focus on: building CI/CD pipelines, maintaining code quality, setting up monitoring, and integrating automated testing. I work with GitHub Actions, Kubernetes, Terraform, and Ansible."*

### 📝 Script — Fresher
> *"I'm passionate about DevOps. I understand the 4 core pillars — automation, quality, monitoring, and testing — and have hands-on experience with Docker and Jenkins through personal projects."*

### 🎙️ Delivery Tips
- Start confidently — no "umm" or "so basically"
- Take 60–90 seconds — more is fine if you have depth
- End with: *"Would you like me to go deeper on any area?"*

### ⚠️ Never Say
- *"I have 10 years of DevOps experience"* — DevOps is only ~7–8 years mainstream
- *"I only do CI/CD"* — cover all 4 pillars

# 📗 Day 2: Software Development Life Cycle (SDLC)

**Goal:** Understand the process every software team follows — and where DevOps fits.

---

## ❓ What is SDLC?

> The **SDLC** is a standard process followed by the software industry to design, develop, and test high-quality software. Every organization — startup or enterprise — follows it.

---

## 🔄 The 5 Phases of SDLC

```
Planning → Design → Build → Test → Deploy
```

| Phase | Who | Output |
|-------|-----|--------|
| **1. Planning & Requirements** | Business Analysts, Product Owners | SRS document |
| **2. Design** | Architects, Senior Engineers | HLD + LLD documents |
| **3. Build (Development)** | Developers | Code committed to Git |
| **4. Testing** | QA / QE Engineers | Bug reports, test results |
| **5. Deployment** | DevOps Engineers | Live production release |

> 🔄 Modern organizations use **Agile sprints** (2–3 week cycles) instead of doing all phases once.

---

## ⚙️ Where DevOps Fits

```
Planning → Design → [BUILD] → [TEST] → [DEPLOY]
                        ↑          ↑        ↑
               DevOps automates these 3 phases
```

> 🎯 DevOps engineers don't write app code — they write **pipelines** that automate Build → Test → Deploy.

### Key Documents
| Short Form | Full Name | Created By |
|---|---|---|
| **SRS** | Software Requirement Specification | Business Analysts |
| **BRD** | Business Requirement Document | Business Analysts |
| **HLD** | High-Level Design | Solution Architects |
| **LLD** | Low-Level Design | Senior Engineers |

### 🎙️ How to Answer "Where does DevOps fit in SDLC?"
> *"DevOps primarily automates the Build, Test, and Deploy phases. Instead of manually deploying code, I write pipelines that automatically build the app, run all tests, and push to production — removing bottlenecks and human error."*

# 📒 Day 3B: Virtual Machines (VMs) — Infrastructure Basics

**Goal:** Understand the infrastructure DevOps engineers manage daily.

---

## 💡 The Core Idea: Efficiency

**The Landlord Analogy:**
```
❌ Inefficient: Own 1 acre → 1 house → Half wasted
✅ Efficient:   Own 1 acre → 2 houses → Both rented → 0 waste
```
Virtualization does the same for servers.

---

## 🧠 How Virtualization Works

```
┌────────────────────────────────────────────┐
│        Physical Server (100GB RAM)          │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐   │
│  │  VM 1   │  │  VM 2   │  │  VM 3   │   │
│  │ (4GB)   │  │ (4GB)   │  │ (4GB)   │   │
│  └─────────┘  └─────────┘  └─────────┘   │
│          Hypervisor (VMware / Xen)          │
└────────────────────────────────────────────┘
```

| Term | Meaning |
|---|---|
| **Physical Server** | Actual hardware (bare metal) from HP/IBM |
| **Hypervisor** | Software that slices physical server into VMs (VMware, Xen) |
| **Virtual Machine** | Logical computer with own OS, CPU, RAM — fully isolated |

**Key:** If VM 1 crashes, VM 2 and VM 3 are **unaffected**.

---

## ☁️ How AWS EC2 Works

```
Your EC2 request → AWS Data Center (Mumbai) → Physical Server → Hypervisor → Your VM
```

AWS sends you an **IP address + key file** to access your virtual machine remotely.

> 📌 Choose your region based on user location to reduce **latency** (e.g., Mumbai for India users).

### 🎙️ Interview Answer
> *"A VM is a logical computer created by partitioning a physical server using a hypervisor like VMware or Xen. Multiple VMs run on the same hardware fully isolated. AWS EC2 instances are VMs provisioned on demand using this same technology."*

# 🟢 Day 7A: Shell Scripting — Zero to Hero

**Goal:** Automate repetitive tasks using shell scripts.

---

## 🔵 What is Shell Scripting?

> Shell scripting = **automating manual Linux tasks** by writing a sequence of commands in a file.

**Why?** If you need to create 1,000 files or check 10,000 servers — you can't do it manually.

---

## 🔵 Writing Your First Script

### File Extension
```bash
myscript.sh    # .sh = shell script (like .py for Python)
```

### The Shebang — First Line of Every Script
```bash
#!/bin/bash
```
- Tells the kernel **which interpreter** to use
- Always use `/bin/bash` (not `/bin/sh` — `sh` may point to `dash` on Ubuntu and break scripts)

### Comments
```bash
# This line is ignored by the computer — for humans only
```

---

## 🔵 Running a Script

```bash
# Create
vim script.sh

# Give permission
chmod 777 script.sh

# Run
./script.sh
```

---

## 🔵 Permissions — The 4-2-1 Rule

| Number | Permission |
|---|---|
| **4** | Read |
| **2** | Write |
| **1** | Execute |
| **7** | Full (4+2+1) |

```bash
chmod 777 script.sh   # Full permissions for User, Group, Others
chmod 600 key.pem     # Read+Write for owner only (required for SSH keys)
```

---

## 🔵 Real-World Use Case

> A DevOps engineer manages **10,000 VMs** at Amazon. He can't manually check each one.

**Solution:** A shell script that:
- Logs into every machine automatically
- Runs `nproc`, `free`, `top` to check health
- Sends an **email alert only if a server is failing**

### 🎙️ Interview Answer
> *"Shell scripting is how I automate repetitive infrastructure tasks. For example, instead of manually checking disk and CPU on 100 servers, I write a script that SSHs into each one, collects metrics, and alerts me only if something is wrong."*

# 🧠 Day 7B: Advanced Shell Scripting

**Goal:** Write production-grade, robust shell scripts.

---

## 1️⃣ Production Safety — The "Set" Commands

```bash
set -x          # Debug mode: prints each command before running it
set -e          # Exit immediately if any command fails
set -o pipefail # Exit if any command in a pipe fails
```

> **Always start production scripts with these 3 lines.**

**Why `set -o pipefail`?** Without it, `command1 | command2` succeeds even if `command1` fails, because only the last command's exit code is checked.

---

## 2️⃣ Script Metadata (Best Practice)

```bash
#!/bin/bash
# Author: Your Name
# Date: 2024-01-01
# Version: v1
# Purpose: Node health check script
set -x
set -e
set -o pipefail
```

---

## 3️⃣ Text Processing — `grep` vs `awk`

| Tool | What It Does | Example |
|---|---|---|
| `grep` | **Filters rows** — keeps lines matching a pattern | `ps -ef \| grep amazon` |
| `awk` | **Filters columns** — extracts specific fields | `awk '{print $2}'` |

**Step-by-step: Find PID of all Amazon processes**
```bash
ps -ef                        # List all processes
ps -ef | grep amazon          # Filter rows: keep Amazon lines only
ps -ef | grep amazon | awk '{print $2}'   # Filter column 2 = PID only
```

### 🎙️ Interview Answer: "grep vs awk?"
> *"`grep` filters rows — it keeps lines that match a pattern. `awk` filters columns — it extracts specific fields from each line. I use both together: grep to narrow down the data, then awk to pull exactly the field I need."*

---

## 4️⃣ Networking: `curl` vs `wget`

| Command | What It Does | When to Use |
|---|---|---|
| `curl` | Fetches content → prints to screen (stdout) | Check API responses, pipe into grep |
| `wget` | Fetches content → saves to disk | Download files to keep locally |

---

## 5️⃣ Finding Files

```bash
find / -name pam.d           # Search entire system for file named "pam.d"
sudo find / -name pam.d      # Use sudo to avoid "Permission Denied" errors
```

---

## 6️⃣ Control Structures

### If-Else
```bash
if [ $a -gt $b ]; then
    echo "a is greater"
else
    echo "b is greater"
fi                           # Note: "fi" closes the if block (if spelled backwards)
```

### For Loop
```bash
for i in {1..100}; do
    echo $i
done
```

---

## 7️⃣ Trap & Signals (Interview Favourite)

**Problem:** User presses `Ctrl+C` while script writes to database → corrupted data.

```bash
# Ctrl+C sends SIGINT signal
trap "rm -rf /tmp/tempfiles && echo 'Cleanup done'" SIGINT
```

> **Trap** catches signals (like Ctrl+C) and runs cleanup code instead of stopping abruptly.

### 🎙️ Interview Answer
> *"The `trap` command lets you handle interruptions gracefully. If a user presses Ctrl+C while a script is running a critical operation, instead of stopping mid-way and leaving corrupted state, `trap` catches the SIGINT signal and runs a cleanup function first."*

# ☁️ Day 7C: AWS Resource Tracker Project

**Goal:** Build a real shell script that tracks AWS resource usage automatically.

---

## 📋 The Business Problem

Cloud resources (EC2, S3, Lambda) left running unused = **wasted money**. A DevOps engineer automates reporting to catch this.

---

## 🛠️ The Script: `aws_resource_tracker.sh`

```bash
#!/bin/bash
# Author: DevOps Engineer
# Date: 2024-01-01
# Version: v1
# Purpose: Track AWS resource usage and generate report

set -x

echo "===== S3 Buckets ====="
aws s3 ls

echo "===== EC2 Instances ====="
aws ec2 describe-instances | jq '.Reservations[].Instances[].InstanceId'

echo "===== Lambda Functions ====="
aws lambda list-functions

echo "===== IAM Users ====="
aws iam list-users
```

---

## 🔑 Key Concepts

| Concept | Tool | Purpose |
|---|---|---|
| JSON parsing | `jq` | Extract only Instance IDs from verbose EC2 JSON output |
| Output redirect | `> report.txt` | Save report to a file instead of just printing |
| Scheduling | **Cron Job** | Auto-run the script daily (e.g., 7 PM every day) |

**Cron Job Example:**
```bash
# Run script every day at 7 PM
0 19 * * * /home/ubuntu/aws_resource_tracker.sh > /home/ubuntu/report.txt
```

### 🎙️ How to Present This Project
> *"I built a shell script that uses the AWS CLI to list all S3 buckets, EC2 instances, Lambda functions, and IAM users. It uses `jq` to parse JSON output cleanly, and I scheduled it with a cron job to run every evening and save the report to a file. This helps the team identify unused resources and control costs."*

# 🧑‍💻 Day 9: Git and GitHub

**Goal:** Understand version control — why it exists and how to use it.

---

## 🔵 Why Version Control?

**Two problems without Git:**
1. **Sharing Code:** How do 10 developers share thousands of files? Not by email.
2. **Versioning:** Requirements change constantly — you need to revert to any past version instantly.

---

## 🔵 Centralized vs Distributed

| Type | Tool | Problem |
|---|---|---|
| **Centralized** | SVN, CVS | Single server = single point of failure |
| **Distributed** | **Git** | Every developer has a full copy — no single point of failure |

---

## 🔵 Git vs GitHub

| | Git | GitHub |
|---|---|---|
| **What** | Open-source command-line tool | Web platform built on top of Git |
| **Purpose** | Track file changes locally | Host code + team collaboration |
| **Alternatives** | — | GitLab, Bitbucket |

---

## 🔵 The Git Lifecycle

```
Working Directory → Staging Area → Local Repo → Remote Repo (GitHub)
      (edit)         git add        git commit      git push
```

| Command | Purpose |
|---|---|
| `git init` | Create a new local repository (creates hidden `.git` folder) |
| `git status` | See which files are untracked or modified |
| `git add <file>` | Stage a file for commit |
| `git commit -m "message"` | Save a version snapshot |
| `git diff` | See exactly what lines changed |
| `git log` | List all commits with IDs and authors |
| `git reset <commit-id>` | Revert to a previous version |
| `git push` | Upload commits to GitHub |
| `git clone <url>` | Download a repository locally |

### 🎙️ Interview Answer: "Explain Git workflow"
> *"First I `git init` to create a repo. As I make changes I use `git add` to stage them and `git commit` to save a snapshot. `git diff` shows line-level changes and `git log` shows full history. When ready to share, `git push` uploads to GitHub. If something breaks, I use `git reset` with a specific commit ID to roll back."*

# 🌳 Day 10: Git Branching Strategy

**Goal:** Understand how teams manage code without breaking production.

---

## 🔵 Why Branches?

Developers can't push experimental code directly to the main product. Branches separate **"stable code"** from **"work in progress"**.

---

## 🔵 The 4 Key Branches

```
Master ─────────────────────────────────────────────→ (always stable)
   │                                       ↑
   ├──► feature-bikes ──────────────────── merge
   │
   ├──► release-v1.27 ──────────────────── (ship to customer)
   │
   └──► hotfix-critical ─────────────────► merge to BOTH master & release
```

| Branch | Purpose | Rule |
|---|---|---|
| **Master/Main** | Source of truth — always latest | No direct development here |
| **Feature** | New functionality (e.g., feature-bikes) | Created from Master, merged back when done |
| **Release** | Prepare a version for the customer | No new features — only final testing |
| **Hotfix** | Emergency fix for a production bug | ⭐ Must merge into **both** Master AND Release |

> 🔑 **The tricky Hotfix rule:** It merges into both branches because:
> - Release branch → fixes the live app
> - Master branch → ensures future versions also have the fix

---

## 🔵 Real-World Example: Kubernetes

- 3,300+ open-source contributors use this strategy
- Active development on `master`
- At release time, they cut `release-1.27` to lock code for testing

### 🎙️ Interview Answer: "Explain your branching strategy"
> *"We follow a standard branching strategy. All development happens in feature branches created from master. Once tested, they're merged back. When a release approaches, we cut a release branch to freeze features and do final testing. For production bugs, we create a hotfix branch and merge it into both the release branch and master to ensure the fix exists everywhere."*

**Goal:** Master advanced Git workflows and common interview scenarios.

## 🔵 The `.git` Folder


## 🔵 Connecting to Remote (GitHub)

| Scenario | Command |
|---|---|

**Standard push workflow:**
```bash

```

## 🔵 Authentication: HTTPS vs SSH

| Method | How | Use When |
|---|---|---|
| **HTTPS** | Username + password/token | Simple, quick setup |
| **SSH** | Public/private key pair | ⭐ Preferred — no password every push |

**SSH Setup:**
```bash

# Copy id_rsa.pub → paste into GitHub Settings → SSH Keys
```

## 🔵 Clone vs Fork (Interview Favourite)

| | Clone | Fork |
|---|---|---|
| **What** | Download repo to your local machine | Create a copy under your GitHub account |
| **When** | Working on a project you have access to | Contributing to someone else's open-source project |
| **Workflow** | `git clone <url>` | Fork → Clone your fork → Make changes → Pull Request |

### 🎙️ Interview Answer
> *"Git clone downloads a repository to your local machine. Git fork creates a server-side copy under your own GitHub account. If I want to contribute to an open-source project like ArgoCD, I fork it first, then clone my fork, make changes, and submit a Pull Request to the original."*

---

## 🔵 Merging Strategies

| Strategy | What It Does | When to Use |
|---|---|---|
| **Cherry Pick** | Take one specific commit from another branch | When you want just one fix, not the whole branch |
| **Merge** | Combines branches, adds on top of history | Non-linear history, simple projects |
| **Rebase** | Replays your commits on top of the latest main | ⭐ Preferred — creates linear, readable history |

```bash
git cherry-pick <commit-id>   # Cherry pick
git merge feature-branch      # Merge
git rebase main               # Rebase
```

### 🎙️ Interview Answer: "Merge vs Rebase?"
> *"Merge combines branches and adds commits on top, creating a non-linear history. Rebase replays your branch commits on top of the latest main, creating a clean linear history. In large teams, rebase is preferred because the log is easier to read and track."*

# ☁️ Day 12: Deploy Your First App to AWS

**Goal:** Take an app from localhost to a live production server on AWS.

---

## 🔵 The Full Deployment Workflow

```
Local Dev → AWS IAM Setup → EC2 Launch → Server Config → Security Groups → Live!
```

---

## Phase 1: Local Sanity Check

```bash
git clone <repo-url>      # Get the code
# Create .env file with secret API keys (never commit this to GitHub!)
npm install               # Install dependencies
npm run start             # Test on localhost:3000
```

> ⚠️ **Never push `.env` (secret keys) to GitHub.** Add it to `.gitignore`.

---

## Phase 2: AWS IAM Setup

> Never use the **Root account** for daily work — security risk.

```
IAM → Create User → Attach Policy (EC2FullAccess or AdministratorAccess) → Login as new user
```

---

## Phase 3: Launch EC2

```
EC2 → Launch Instance → Ubuntu → t2.micro (Free Tier) → Create Key Pair → Launch
```

```bash
chmod 400 demo.pem                           # Secure the key file
ssh -i demo.pem ubuntu@<public-ip>           # Connect to the server
```

---

## Phase 4: Configure the Server

```bash
sudo apt update                  # Refresh package manager
# Install Node.js and NPM
git clone <repo-url>             # Clone the app
vim .env                         # Recreate secret keys on the server
npm run start                    # Start the app on the cloud server
```

---

## Phase 5: Open Firewall (The Magic Step ⭐)

> App is running but **nobody can access it**. Why? AWS blocks all traffic by default.

```
EC2 → Security Groups → Inbound Rules → Add Rule:
  Type: Custom TCP | Port: 3000 | Source: 0.0.0.0/0
```

Now anyone can access `http://<public-ip>:3000`!

### 🎙️ Interview Answer: "How do you deploy an app to AWS?"
> *"I create an EC2 instance with Ubuntu, connect via SSH using the key pair, install the required runtime (Node.js, Java, etc.), clone the repo, and configure any environment variables. The key step people miss is opening the right port in the Security Group — by default AWS blocks all traffic except SSH on port 22."*

# ⚙️ Day 14: Configuration Management with Ansible

**Goal:** Understand why Ansible exists and how it works — and ace the Ansible interview questions.

---

## 🔵 The Problem: Scaling Server Management

Old way: Manually SSH into 50 servers, run updates, install software.
- Scripts helped but broke when OS versions changed
- Cloud-scale = thousands of servers → scripts became unmanageable

---

## 🔵 The Solution: Configuration Management

> Write the configuration **once** — the tool ensures it applies **everywhere**.

---

## 🔵 Ansible vs Puppet (The Most Asked Interview Topic)

| Feature | Puppet (Old) | Ansible (Modern) |
|---|---|---|
| **Model** | Pull — agents ask master for updates | **Push** — you push code to servers |
| **Architecture** | Master-Slave with agents on every server | **Agentless** — no installation on targets |
| **Language** | Puppet DSL (complex) | **YAML** (simple, human-readable) |
| **Built On** | — | **Python** |
| **Learning Curve** | High | Low |

---

## 🔵 How Ansible Connects (Agentless)

```
Ansible Master → SSH → Linux Servers
Ansible Master → WinRM → Windows Servers
```

> Ansible only needs an **IP address** and a valid connection. It doesn't care if the server is on AWS, Azure, or GCP.

---

## 🔵 Ansible Galaxy

> Community hub (like Docker Hub) where engineers share reusable Ansible modules.

---

## 🔵 Limitations of Ansible

| Limitation | Detail |
|---|---|
| Windows support | Still trickier than Linux despite improvements |
| Debugging | Error logs can be hard to read |
| Performance | SSH-based push can be slow at massive scale (10,000+ servers) |

---

## 🔵 Top 6 Ansible Interview Q&A

| Question | Answer |
|---|---|
| What language is Ansible built on? | **Python** |
| Does it support Windows? | **Yes, via WinRM** |
| Push or Pull? | **Push** |
| File format? | **YAML** |
| Puppet vs Ansible? | Push/Agentless vs Pull/Agent-based |
| Supports all clouds? | **Yes** — connects via IP/SSH, cloud-agnostic |

### 🎙️ Interview Answer: "Why Ansible over Puppet?"
> *"Ansible is agentless — you don't need to install anything on the target servers, it uses existing SSH. Puppet requires installing and maintaining agents on every server. Ansible uses simple YAML playbooks while Puppet has its own complex DSL. Ansible is also a push model, giving you direct control, whereas Puppet uses a pull model where agents check in periodically."*

# ⚙️ Day 15: Ansible Zero to Hero (Practical)

**Goal:** Install Ansible, connect to servers, run commands, and write playbooks.

---

## 🔵 Setup: 2-Server Architecture

```
[Ansible Master]  →  SSH (passwordless)  →  [Target Node]
(write playbooks here)                    (tasks run here)
```

```bash
# On Master: Install Ansible
sudo apt update
sudo apt install ansible
ansible --version    # Verify
```

---

## 🔵 Passwordless SSH Setup

```bash
# On Master: Generate key pair
ssh-keygen

# Copy public key content:
cat ~/.ssh/id_rsa.pub

# On Target Node: Paste into:
~/.ssh/authorized_keys

# Test from Master:
ssh <target-ip>     # Should log in with NO password prompt
```

---

## 🔵 Inventory File

```ini
# inventory.txt
[webservers]
192.168.1.10
192.168.1.11

[dbservers]
192.168.1.20
```

---

## 🔵 Ad-Hoc Commands (Quick, One-Off Tasks)

```bash
# Syntax
ansible -i inventory <group> -m <module> -a "<arguments>"

# Create a file called "test" on all servers
ansible -i inventory all -m shell -a "touch test"

# Check disk space on webservers
ansible -i inventory webservers -m shell -a "df -h"
```

---

## 🔵 Playbooks (Multi-Step Automation)

```yaml
---
- name: Install and start Nginx
  hosts: webservers
  become: yes           # Run as sudo/root

  tasks:
    - name: Install Nginx
      apt:
        name: nginx
        state: present  # Ensure it's installed

    - name: Start Nginx
      service:
        name: nginx
        state: started  # Ensure it's running
        enabled: yes
```

```bash
# Run the playbook
ansible-playbook -i inventory first-playbook.yaml

# Debug mode (verbose output)
ansible-playbook -i inventory first-playbook.yaml -v
```

---

## 🔵 Ansible Roles (Organizing Large Projects)

```bash
# Auto-generate role folder structure
ansible-galaxy role init my_role
```

**Folder Structure:**
```
my_role/
├── tasks/          # Main steps (main.yaml)
├── vars/           # Variables (port numbers, package names)
├── defaults/       # Default variable values
├── files/          # Static files (SSL certificates)
├── templates/      # Dynamic files (HTML templates)
└── handlers/       # Actions triggered by changes (e.g., "Restart Nginx")
```

### 🎙️ Interview Answer: "Ad-hoc vs Playbook?"
> *"Ad-hoc commands are for quick, one-time tasks — like checking disk space across all servers with a single command. Playbooks are for complex, repeatable workflows written in YAML, like installing and configuring a full application stack. Roles are how I organize large playbooks into reusable, structured components."*
