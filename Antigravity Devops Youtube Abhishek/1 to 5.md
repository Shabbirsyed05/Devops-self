# 📘 Day 1: Fundamentals of DevOps

**Course Status:** Day 1 of 40 | **Goal:** Understand What and Why of DevOps before any tools.

---

## 🤔 What is DevOps?

### Simple Definition
> DevOps is a **culture or practice** adopted by an organization to improve its ability to **deliver applications faster and more reliably**.

### Interview-Ready Definition
> *"DevOps is a process of improving application delivery by ensuring proper automation, maintaining quality, and implementing continuous monitoring and testing."*

### Real-World Example
| Without DevOps | With DevOps |
|---|---|
| A bug fix takes **10–30 days** to reach users | Bug fix reaches users in **hours or minutes** |
| Manual hand-offs between siloed teams | Automated pipelines handle everything |
| Slow, inconsistent deployments | Fast, repeatable, reliable releases |

> 🎮 Think of Android pushing a security patch overnight — **that's DevOps.**

---

## 🏛️ The 4 Pillars of DevOps

> ⚠️ **Memorize these.** Every DevOps interview question leads back to these 4 pillars.

```
╔══════════════════════════════════════════════╗
║          4 PILLARS OF DEVOPS                 ║
╠══════════════════════════════════════════════╣
║  🤖 Automation  → Remove all manual steps   ║
║  ✅ Quality     → App works before shipping ║
║  📊 Monitoring  → Detect issues proactively ║
║  🧪 Testing     → Validate at every stage   ║
╚══════════════════════════════════════════════╝
```

| Pillar | What It Means | Why It Matters |
|--------|--------------|----------------|
| 🤖 **Automation** | Replace manual tasks with scripts/tools | Manual = slow and error-prone |
| ✅ **Quality** | App must meet standards before delivery | Fast delivery is useless if it's broken |
| 📊 **Monitoring** | Watch systems 24/7 for issues | You can't fix what you can't see |
| 🧪 **Testing** | Automated tests at every stage | Catch bugs before they reach users |

> 📝 **Note:** Monitoring and Observability are used interchangeably — same concept, say either in interviews.

---

## ⏳ Why DevOps? (The Evolution Story)

> 🎯 **Interview Tip:** This "before vs after" story shows you understand the *purpose*, not just the tools.

### ❌ Before DevOps (~10 years ago)
```
Developer → [SVN / Code Repo] → System Admin → Build & Release Eng → Tester → Production
```

| Old Role | What They Did |
|---|---|
| **System Administrator** | Created & managed servers (VMware, OpenStack, bare metal) |
| **Build & Release Engineer** | Packaged and deployed app to server |
| **Server Administrator** | Set up the application server (Tomcat, Apache) |
| **Tester** | Manually tested the app on each environment |

**Problems:**
- ❌ 100% manual → slow and error-prone
- ❌ Siloed teams → poor communication
- ❌ Deployments took weeks or months
- ❌ No consistency between environments

### ✅ After DevOps
- ✅ One unified culture, shared responsibility
- ✅ Automated pipelines replace manual steps
- ✅ Delivery drops from weeks → **hours**
- ✅ Continuous feedback through monitoring and testing

> 💬 **Why is DevOps a "culture" not a "tool"?**
> Because it requires people to *continuously adapt and adopt* better practices. A tool can be installed — culture must be built.

## 🎤 How to Introduce Yourself (DevOps Interview)

> ⚠️ **This is where most candidates fail.** The interviewer decides within the first 5 minutes.

### ✅ 4-Step Introduction Framework
```
Step 1 → Current Role + Years of Experience
Step 2 → Previous Background (your bridge into DevOps)
Step 3 → Day-to-Day Responsibilities (use the 4 pillars!)
Step 4 → Tools & Technologies (mention only what you know)
```

### 📝 Script — Experienced Candidate
> *"I'm a DevOps Engineer with 4–5 years of experience. Before this, I worked as a System Administrator, which gave me strong server fundamentals. In my current role, I focus on:*
> - *Building automated CI/CD pipelines*
> - *Maintaining code and application quality*
> - *Setting up continuous monitoring and alerting*
> - *Integrating automated testing into every release*
>
> *I work with GitHub Actions for CI/CD, Kubernetes for orchestration, Terraform for infrastructure, and Ansible for configuration management."*

### 📝 Script — Fresher Candidate
> *"I'm passionate about DevOps and have been actively learning it through hands-on projects. I understand the four core pillars — automation, quality, monitoring, and testing — and I've built CI/CD pipelines and worked with Docker and Jenkins in my practice projects."*

### ⚠️ Mistakes to Avoid
| ❌ Don't Say | ✅ Instead |
|---|---|
| "I have 10 years of DevOps experience" | DevOps is ~7–8 years old — this is a red flag |
| "I only do CI/CD" | Cover all 4 pillars |
| Skip your past background | Connect your history to DevOps |
| List tools without knowing them | Only mention tools you can explain |

### 🎙️ How to Deliver It
- Start **confidently** — no "umm" or "so basically"
- Take your time — **60–90 seconds is perfect**, more is OK
- Use **real examples** — makes answers memorable
- End with: *"Would you like me to go deeper on any area?"*

# 📗 Day 2: Software Development Life Cycle (SDLC)

**Goal:** Understand the process every software team follows — and where DevOps fits in it.

---

## ❓ What is SDLC?

> The **Software Development Life Cycle (SDLC)** is a standard process followed by the software industry to design, develop, and test high-quality software.

Every organization — startup or enterprise (like Amazon) — follows this process. Developers, testers, and DevOps engineers all work within it.

---

## 🔄 The 5 Phases of SDLC

*Using the example of example.com launching a new kids' clothing section:*

### 1️⃣ Planning & Requirements Gathering
- **Who:** Business Analysts, Product Owners
- **What:** Research what customers need, validate the idea
- **Output:** **SRS — Software Requirement Specification** document
- *"Is there demand for kids' clothing? Which age groups? What price range?"*

### 2️⃣ Defining & Designing
- **Who:** Architects, Senior Engineers
- **What:** Plan the technical structure
- **Output:**
  - **HLD (High-Level Design):** Big picture — scalability, database choice, system architecture
  - **LLD (Low-Level Design):** Specific logic — function calls, SQL queries, API contracts

### 3️⃣ Building (Development)
- **Who:** Developers
- **What:** Write the code based on design documents
- **Tool:** Code is stored in a shared repository — **Git**

### 4️⃣ Testing
- **Who:** QA / QE Engineers
- **What:** Deploy code to a test server, find and report bugs before release

### 5️⃣ Deployment
- **Who:** DevOps Engineers
- **What:** Push the tested app to **production** (live, real users)
- **Modern approach:** Done in **Agile sprints** (2–3 week cycles), not all at once

---

## ⚙️ Where DevOps Fits in SDLC

```
Planning → Design → [BUILD] → [TEST] → [DEPLOY]
                        ↑           ↑         ↑
                   DevOps automates these 3 phases
```

> 🎯 **DevOps engineers don't write app code or test manually.**
> They write **scripts and pipelines** to make Build → Test → Deploy happen **automatically**.

### Key Documents to Know for Interviews
| Document | Full Name | Created By |
|---|---|---|
| **SRS** | Software Requirement Specification | Business Analysts |
| **HLD** | High-Level Design | Solution Architects |
| **LLD** | Low-Level Design | Senior Engineers |

### 🎙️ How to Answer "Where does DevOps fit in SDLC?"
> *"DevOps primarily focuses on automating the Build, Test, and Deploy phases of the SDLC. Instead of manually deploying code, I write pipelines that automatically build the application, run all tests, and push it to production — removing human error and bottlenecks from the process."*

# 📙 Day 3A: DevOps Engineer — Organizational Context & Roles

**Goal:** Understand how work actually reaches a DevOps engineer inside a real company.

---

## 🔗 The Chain of Command (How Requirements Flow)

*Example: Amazon Fresh wants to offer 15-minute grocery delivery*

```
Customer → Business Analyst → Product Manager → Product Owner → Architect → Scrum Team (YOU)
```

| Role | Responsibility |
|---|---|
| **Customer** | Provides the initial need or feedback |
| **Business Analyst (BA)** | Gathers requirements, creates **BRD (Business Requirement Document)** |
| **Product Manager (PM)** | Prioritizes features, decides *when* to build, tracks competitors |
| **Product Owner (PO)** | Breaks PM vision into **Epics & Stories**, defines "done" |
| **Solutions Architect (SA)** | Creates **HLD/LLD**, checks technical feasibility |
| **Scrum Team** | Developers, QA, **DevOps**, DBAs — actually builds the feature |

> 💡 **Key Insight:** DevOps engineers **never deal directly with external customers**. Work arrives through the internal chain.

---

## 👥 How DevOps Gets Tasks

**Example workflow:**
1. Developer needs to build the *"15-minute delivery"* feature
2. Developer needs: a Kubernetes cluster, a Dockerfile, a Git repo
3. Those infrastructure tasks are assigned to the **DevOps engineer**
4. DevOps also proactively identifies automation gaps (e.g., converting manual testing to CI/CD)

### Beyond Requests — Proactive DevOps
- Identify manual processes and automate them
- After launch: **Site Reliability Engineers (SRE)** take over monitoring
- DevOps and SRE roles often overlap

---

## 📋 Project Management with Jira

| Jira Term | What It Means | Example |
|---|---|---|
| **Epic** | Large body of work | "Enable 15-minute delivery" |
| **Story** | Smaller task broken from an Epic | "Create AWS RDS Database" |
| **Sprint** | 2–3 week cycle to complete stories | Team commits to 5 stories this sprint |
| **Backlog** | Queue of pending tasks | Stories waiting for next sprint |

### 🎙️ How to Explain Your Role in an Interview
> *"In my organization, I work within a Scrum team. I receive tasks primarily from developers who need infrastructure or from architecture design documents. I track my work in Jira — breaking down Epics into Stories and completing them sprint by sprint. I also proactively identify opportunities to automate manual processes in the pipeline."*

# 📒 Day 3B: Virtual Machines (VMs) — Infrastructure Basics

**Goal:** Understand the infrastructure layer that DevOps engineers manage daily.

---

## 💡 The Core Concept: Efficiency

> **DevOps is about efficiency** — never waste resources.

### The Landlord Analogy
```
❌ INEFFICIENT: Own 1 acre → Build 1 house → Half acre wasted
✅ EFFICIENT:   Own 1 acre → Build 2 houses → Rent out both → 0 waste
```
**Virtualization does the same for servers.**

---

## 🚫 The Problem: Physical Server Waste

- A company buys a physical server with **100GB RAM** from HP or IBM
- Their app only needs **4GB RAM**
- **96GB sits completely idle** — wasted money
- Old model: **1 physical server = 1 team** → 100 servers for 100 teams

---

## 🧠 The Solution: Virtualization & Hypervisors

```
┌─────────────────────────────────────────────┐
│         Physical Server (100GB RAM)          │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │  VM 1    │  │  VM 2    │  │  VM 3    │  │
│  │ (4GB)    │  │ (4GB)    │  │ (4GB)    │  │
│  └──────────┘  └──────────┘  └──────────┘  │
│           Hypervisor (VMware / Xen)          │
└─────────────────────────────────────────────┘
```

| Term | Simple Meaning |
|---|---|
| **Physical Server** | The actual hardware (bare metal) from HP/IBM |
| **Hypervisor** | Software that splits one physical server into multiple VMs (e.g., VMware, Xen) |
| **Virtual Machine (VM)** | A logical computer with its own OS, CPU, RAM — lives inside a physical server |

**Key Feature:** If VM 1 crashes, VM 2 and VM 3 are **unaffected**. Full logical isolation.

---

## ☁️ How AWS Uses Virtualization

```
Your Request (EC2) → AWS Data Center (Mumbai) → Physical Server → Hypervisor → Your VM
```

1. AWS owns massive data centers globally (Mumbai, Singapore, Ohio, etc.)
2. You request an EC2 instance via the AWS portal
3. AWS finds a physical server with free space
4. The hypervisor creates a logical slice for you
5. AWS sends you an **IP address + key** to access it remotely

> 📌 **Latency:** Choose your data center region based on your users' location (e.g., choose Mumbai if your users are in India).

### 🎙️ How to Explain VMs in an Interview
> *"A Virtual Machine is a logical computer created by partitioning a physical server using a hypervisor like VMware or Xen. This allows multiple isolated environments to run on the same hardware, improving resource utilization. In cloud computing, AWS EC2 instances are essentially VMs provisioned on demand."*

# 📕 Day 4: Creating Virtual Machines — AWS & Azure

**Goal:** Move from theory to practice — create your first VM and understand automation.

---

## 🔁 Manual vs. Automated VM Creation

| Approach | How | Who Does It | Scale |
|---|---|---|---|
| **Manual (UI)** | Click buttons in the browser console | Anyone | Works for 1–5 VMs |
| **Automated (DevOps)** | Write a script that calls the cloud API | DevOps Engineer | Works for 1–1000 VMs |

> 🎯 **The DevOps Principle:** If you do something more than once, automate it.

---

## 🛠️ Automation Tools for Cloud (AWS)

| Tool | Type | Best For |
|---|---|---|
| **AWS CLI** | Command Line | Simple terminal-based tasks |
| **Boto3** | Python SDK | Scripted, programmatic control |
| **CloudFormation (CFT)** | AWS-native YAML/JSON | AWS-only infrastructure |
| **AWS CDK** | AWS-native code | Gets new AWS features fastest |
| **Terraform** | Open Source / Multi-Cloud | ⭐ Industry standard — works on AWS, Azure, GCP |

> 💡 **Terraform Tip:** If your company uses **multi-cloud or hybrid cloud** (e.g., AI on GCP + storage on AWS), Terraform is the best choice because it manages all platforms from one place.

---

## 🧪 Practical Lab: Creating an EC2 Instance (AWS)

```
AWS Console → EC2 → Launch Instance → Configure → Download Key → Launch
```

| Step | What To Do | Key Note |
|---|---|---|
| 1 | Create AWS account | Requires card for identity verification |
| 2 | Go to EC2 service | EC2 = Elastic Compute Cloud = AWS name for VM |
| 3 | Click "Launch Instance" | — |
| 4 | Select OS | Choose **Ubuntu** (most widely used in DevOps) |
| 5 | Select instance type | ⭐ Always pick **t2.micro (Free Tier)** — 750 hrs/month free |
| 6 | Create Key Pair | Download the `.pem` file |
| 7 | Launch | ✅ Done |

> ⚠️ **Critical Warning:** The `.pem` key file = your password. **Lose it = lose access to your server forever.**

---

## ☁️ AWS vs Azure Quick Comparison

| Feature | AWS | Azure |
|---|---|---|
| Free Tier | ~12 months | ~30–45 days |
| Login | AWS account | Can use GitHub account |
| VM Name | **EC2 Instance** | **Virtual Machine** |
| Best For | Long-term practice | Quick exploration |

# 📓 Day 5: Connecting to VMs & AWS CLI Automation

**Goal:** Access your EC2 instance from your laptop and automate AWS with the CLI.

---

## 🔌 Two Ways to Connect to Your EC2 Instance

### Method A: AWS Instance Connect (Browser)
```
AWS Console → Select Instance → Click "Connect" → Browser Terminal Opens
```
- ✅ Zero setup
- ❌ Times out quickly
- ❌ Not practical for daily DevOps work

### Method B: SSH from Terminal (The DevOps Way ⭐)

```bash
ssh -i <your-key.pem> ubuntu@<public-ip-address>
```

| Part | Meaning |
|---|---|
| `ssh` | Secure Shell protocol |
| `-i <key.pem>` | Your identity/key file |
| `ubuntu` | Default username for Ubuntu EC2 |
| `<public-ip>` | Your instance's public IP from AWS console |

**Best Terminal Tools:**
| OS | Recommended Tool |
|---|---|
| Mac | iTerm |
| Windows | **MobaXterm** (recommended) or Git Bash |

> 🪟 **Windows Users:** Use **MobaXterm** — it's simpler than PuTTY and works with `.pem` files directly. PuTTY requires converting to `.ppk` format.

---

## ⚠️ Critical Troubleshooting: Permission Error Fix

**Error you'll see:**
```
Permission denied (publickey)
WARNING: UNPROTECTED PRIVATE KEY FILE!
Permissions 0644 for 'key.pem' are too open
```

**Why it happens:** Your `.pem` file is readable by other users on your system.

**Fix (Mac/Linux):**
```bash
chmod 600 your-key-name.pem
```

> 🔐 This is a **mandatory security step** — AWS blocks access if the key file has open permissions.

---

## 🤖 AWS CLI — Automate Everything from Terminal

### Why CLI over Console?
> Clicking 100 buttons = slow + error-prone. One CLI command = fast + repeatable.

### Step 1: Install
```bash
# Verify after installing
aws --version
```

### Step 2: Create Access Keys (Your "CLI Password")
```
AWS Console → Click your name (top right) → Security Credentials → Create Access Key
```

> ⚠️ **You see the Secret Access Key ONLY ONCE. Save it immediately.**

| Key Type | What It Is |
|---|---|
| **Access Key ID** | Like a username |
| **Secret Access Key** | Like a password — never share this |

### Step 3: Configure CLI
```bash
aws configure
```
Enter when prompted:
- Access Key ID
- Secret Access Key
- Default region (e.g., `ap-south-1` for Mumbai)
- Output format: `json`

### Step 4: Test It
```bash
# List all S3 buckets — no browser needed!
aws s3 ls

# List all running EC2 instances
aws ec2 describe-instances
```

---

## 🔗 Connecting from Windows (MobaXterm Step-by-Step)

| Step | Action |
|---|---|
| 1 | Download & install MobaXterm (Home/Community Edition) |
| 2 | Open → Click **Session** → Select **SSH** |
| 3 | **Remote Host:** Paste EC2 public IP |
| 4 | **Username:** `ubuntu` |
| 5 | Advanced SSH settings → Check **Use private key** → Browse to `.pem` file |
| 6 | Click OK → You're in! |

### 🎙️ How to Explain EC2 Access in an Interview
> *"To connect to an EC2 instance, I use SSH from the terminal with the private key file generated during instance creation. On Windows, I use MobaXterm for a cleaner experience. For automation, I use the AWS CLI, which I configure with access keys using `aws configure`. This allows me to manage infrastructure from scripts instead of clicking through the console."*

## 🗣️ Universal Interview Speaking Tips

| ✅ DO | ❌ DON'T |
|---|---|
| Start with a clear, confident opening sentence | Start with "umm", "so basically", "kind of" |
| Number your points: "First… Second… Third…" | Speak in one long, run-on answer |
| Use real-world analogies (PUBG, Android, landlord) | Give only textbook definitions |
| Pause between key ideas | Rush through the answer nervously |
| Offer to go deeper: *"Should I elaborate?"* | Monologue without checking the interviewer |
| Mention only tools you truly know | Drop tool names you can't explain |
| Connect past experience to DevOps | Pretend you have no non-DevOps history |
