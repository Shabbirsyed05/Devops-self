# 🔄 Day 18: What is CI/CD?

**Goal:** Understand the automated bridge between developer code and customer delivery.

---

## 🔵 The Core Problem

```
Developer writes code on laptop → Customer is across the globe

Manual process:
  → Manual testing    (days)
  → Manual security   (days)
  → Manual deployment (days)
  → Total: weeks/months per release ❌
```

---

## 🔵 The Solution: CI/CD

| Term | Full Form | What It Does |
|---|---|---|
| **CI** | Continuous Integration | Validates code automatically the moment a developer commits |
| **CD** | Continuous Delivery | Deploys the validated app to a platform for customers |

```
Developer commits → CI kicks in → CD delivers → Customer uses it
```

---

## 🔵 The 5 Standard Pipeline Stages

| Stage | What It Checks | Example |
|---|---|---|
| **1. Unit Testing** | Individual function logic | `2 + 3 = 5` for a calculator app |
| **2. Static Code Analysis** | Syntax, formatting, unused variables | 20 variables declared, only 2 used |
| **3. Vulnerability Testing** | Security bugs, outdated dependencies | Old library with known CVE |
| **4. Functional Testing** | New change didn't break old features | Adding subtraction shouldn't break addition |
| **5. Reporting & Deployment** | Package results, deploy to target | Deploy to EC2 or Kubernetes |

---

## 🔵 Architecture: Jenkins (Legacy) vs GitHub Actions (Modern)

### 🏗️ Jenkins — Legacy Orchestrator

```
Git Repo → Jenkins Master watches → triggers Maven/SonarQube → Deploy
           (VM running 24/7)
```

| Problem | Detail |
|---|---|
| **Cost inefficiency** | EC2 servers run even on weekends when no one commits |
| **Idle resources** | Paying for compute with zero work being done |
| **Maintenance** | Managing agents, plugins, upgrades manually |

---

### ⚡ GitHub Actions — Modern Event-Driven

```
Developer creates PR
        ↓
GitHub Actions triggers (event-driven)
        ↓
Temporary Runner (container) created
        ↓
Tests run
        ↓
Container destroyed ✅ (zero idle cost)
```

**Key benefit:** No idle servers. Zero cost when no code is being committed.

---

## 🔵 The 3 Environments (How Code Reaches Production)

> Code never goes **directly** from developer laptop to production.

```
Dev → Staging → Production
```

| Environment | Purpose | Scale |
|---|---|---|
| **Dev** | Initial functional testing | Single server |
| **Staging** | Pre-production mirror | Fewer resources (5 nodes vs 30) |
| **Production** | Real customers | Fully scaled, highly available |

### 🎙️ Interview Answer: "What is CI/CD?"
> *"CI/CD is the automated pipeline that bridges developer code commits and customer delivery. CI — Continuous Integration — validates code immediately after a commit through unit tests, static analysis, and security scanning. CD — Continuous Delivery — then deploys the validated artifact to the target environment. The pipeline typically covers five stages: unit testing, static code analysis, vulnerability scanning, functional testing, and deployment. Tools like Jenkins or GitHub Actions automate this entire process."*

# 🔧 Day 19: Jenkins Zero to Hero

**Goal:** Install Jenkins, configure Docker agents, and run real CI/CD pipelines.

---

## 🔵 Installation on AWS EC2

```bash
# 1. Launch Ubuntu EC2 instance
# 2. Install Java (Jenkins prerequisite)
sudo apt update
sudo apt install openjdk-11-jdk -y

# 3. Install Jenkins (follow jenkins.io for repo key + apt install)
sudo apt install jenkins -y

# 4. Start Jenkins
sudo systemctl start jenkins
sudo systemctl enable jenkins

# 5. Get initial admin password
sudo cat /var/lib/jenkins/secrets/initialAdminPassword
```

**Port:** Jenkins runs on **Port 8080** by default.

> ⚠️ **Must open Port 8080 in AWS Security Group (Inbound Rules)** — otherwise UI won't load.

---

## 🔵 Architecture: Old Way vs Modern Way

| Architecture | How | Problems |
|---|---|---|
| **Old — Static Agents** | Permanent EC2 instances (worker nodes) attached to master | ❌ Expensive: idle 24/7 |
| | | ❌ Messy: dependency conflicts (Java 8 vs Java 11 on same node) |
| **New — Docker Agents** | Jenkins spins up a container per job, destroys it after | ✅ No idle cost |
| | | ✅ Clean: each job gets a fresh, isolated environment |

---

## 🔵 Enabling Docker Agents

```bash
# 1. Install Docker on Jenkins server
sudo apt install docker.io -y

# 2. Add jenkins user to docker group (CRITICAL)
sudo usermod -aG docker jenkins

# 3. Restart Jenkins
sudo systemctl restart jenkins
```

---

## 🔵 The Jenkinsfile (Pipeline as Code)

> Jenkins pipelines are defined in a `Jenkinsfile` stored in the Git repo.

```groovy
pipeline {
    agent {
        docker {
            image 'maven:3.8-openjdk-11'   // Docker container as agent
        }
    }
    stages {
        stage('Checkout') {
            steps {
                git 'https://github.com/user/repo.git'
            }
        }
        stage('Build') {
            steps {
                sh 'mvn clean package'
            }
        }
        stage('Test') {
            steps {
                sh 'mvn test'
            }
        }
        stage('Deploy') {
            steps {
                sh './deploy.sh'
            }
        }
    }
}
```

**Key concept:** The `agent { docker { image 'maven:...' } }` block means Jenkins creates a Maven container for this job and destroys it after — no permanent agent needed.

---

## 🔵 Essential Jenkins Plugins

> *"Memorize 5–10 plugins before interviews."*

| Plugin | Purpose |
|---|---|
| **Git** | Connect to GitHub/GitLab repositories |
| **Maven Integration** | Build Java projects |
| **Docker Pipeline** | Use Docker containers as agents |
| **SonarQube Scanner** | Static code analysis integration |
| **Blue Ocean** | Modern, visual pipeline UI |
| **Credentials Plugin** | Store secrets securely |

### 🎙️ Interview Answer: "Jenkins Master vs Agent?"
> *"The Jenkins Master handles scheduling, the UI, and pipeline orchestration. Agents (nodes) are where the actual work runs. In the modern Docker agent approach, instead of maintaining permanent EC2 worker nodes, Jenkins dynamically spins up a Docker container for each job and destroys it when done. This eliminates idle resource costs and dependency conflicts between jobs."*

# ⚡ Day 20: GitHub Actions

**Goal:** Understand GitHub's native CI/CD platform and when to use it vs Jenkins.

---

## 🔵 What is GitHub Actions?

> A CI/CD platform **built directly into GitHub** — no server to provision or maintain.

- **Type:** SaaS (Software as a Service)
- **Scope:** Works only with code hosted on **GitHub** (not GitLab, not Bitbucket)
- **Vs Jenkins:** No separate server — GitHub manages the runners

---

## 🔵 Pipeline Structure

**File location:**
```
.github/workflows/ci.yaml
```

> ⚠️ **Must be in exactly this path** — GitHub won't detect it otherwise.

**You can have multiple workflow files** running simultaneously:
- `ci.yaml` — for testing
- `security.yaml` — for vulnerability scanning
- `pr-title.yaml` — for PR naming rules

---

## 🔵 Anatomy of a GitHub Actions Workflow

```yaml
name: Python CI Pipeline

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest        # Runner = temporary GitHub-managed container

    steps:
      - name: Checkout Code
        uses: actions/checkout@v3   # Action (reusable plugin)

      - name: Set up Python
        uses: actions/setup-python@v4
        with:
          python-version: '3.9'

      - name: Install Dependencies
        run: pip install -r requirements.txt

      - name: Run Tests
        run: pytest
```

---

## 🔵 Key Components

| Component | Definition | GitHub Actions |
|---|---|---|
| **Runner** | Where the code runs | `runs-on: ubuntu-latest` — temp container from GitHub |
| **Job** | Collection of steps | Can have multiple jobs in one workflow |
| **Step** | Specific task | "Checkout", "Install Python", "Run Tests" |
| **Action (Plugin)** | Reusable code block | `uses: actions/checkout@v3` — no installation needed |

---

## 🔵 Advanced Features

### Matrix Testing
```yaml
strategy:
  matrix:
    python-version: [3.8, 3.9, 3.10]    # Runs tests on all 3 versions simultaneously
```

### Secrets Management
```
GitHub → Repository → Settings → Secrets and Variables → Add Secret
```
```yaml
env:
  SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}   # Inject secret safely
```

### Self-Hosted Runners
> Use your own server instead of GitHub's runners — for private security requirements.

---

## 🔵 GitHub Actions vs Jenkins

| Feature | Jenkins | GitHub Actions |
|---|---|---|
| **Hosting** | Self-hosted (you maintain it) | GitHub manages it |
| **Cost** | Pay for EC2 even when idle | Free for public repos; 2000 min/month for private |
| **Plugins** | Manually installed/updated by admin | Used directly from Marketplace in YAML |
| **Portability** | ✅ Any cloud/platform | ❌ GitHub ecosystem only |
| **Setup** | Complex (Master + agents) | Zero setup |
| **Best for** | Enterprise, multi-cloud, complex pipelines | GitHub-hosted projects, open source |

### 🎙️ Interview Answer: "Jenkins vs GitHub Actions?"
> *"Jenkins is self-hosted — you provision and maintain the server, but it gives you full portability across clouds. GitHub Actions is managed — GitHub handles the infrastructure, and you just write YAML. Actions are free for public repos and have a 2000 minute monthly limit for private repos. I choose Jenkins when we need complex multi-cloud pipelines or enterprise integrations, and GitHub Actions when the code is on GitHub and we want zero maintenance overhead."*

# 🎤 Day 21: CI/CD Interview Questions

**Goal:** Answer scenario-based CI/CD interview questions with depth and confidence.

---

## 🔵 Q1: "Explain your CI/CD Process" — The Golden Question

> ⚠️ **Never say just "I use Jenkins."** Describe the full tool flow.

### 🎙️ Full Answer (Java App Example)
> *"A developer commits code to GitHub. This event triggers our Jenkins pipeline via a Webhook. Jenkins checks out the code and uses Maven to build the artifact. We then run static analysis with SonarQube and security scanning with AppScan. Once validated, ArgoCD (GitOps) deploys the new container image to our Kubernetes cluster. The whole process takes about 10–15 minutes from commit to production."*

**The tool chain:**
```
GitHub → (Webhook) → Jenkins → Maven (build) → SonarQube (quality)
       → AppScan (security) → Docker image → ArgoCD → Kubernetes
```

---

## 🔵 Q2: Polling vs Webhooks — How Jenkins Knows to Start

| Method | How | Verdict |
|---|---|---|
| **Poll SCM** | Jenkins checks GitHub every few minutes | ❌ Wastes CPU and network — inefficient |
| **Build Trigger (Cron)** | Runs on a schedule | ❌ Delayed — not real-time |
| **Webhook** ⭐ | GitHub sends a JSON payload the moment an event occurs | ✅ Best practice — event-driven, immediate |

### 🎙️ Answer
> *"We use Webhooks. Jenkins Poll SCM is inefficient — it's constantly checking GitHub even when nothing changed. A Webhook is event-driven: GitHub sends a notification to Jenkins only when code is pushed or a PR is created. This triggers the pipeline immediately with zero wasted compute."*

---

## 🔵 Q3: Handling Secrets Securely

| Approach | How | Level |
|---|---|---|
| **Jenkins Credentials Plugin** | Native secrets store in Jenkins | Basic |
| **HashiCorp Vault** ⭐ | External enterprise-grade secrets manager | Pro / Enterprise |

### 🎙️ Pro Answer
> *"For basic setups, we use the Jenkins Credentials Plugin to store tokens and passwords. For enterprise environments, we integrate HashiCorp Vault — secrets are stored centrally, rotated automatically, and Jenkins fetches them at runtime without storing them on disk. This prevents secrets from appearing in pipeline logs or build artifacts."*

---

## 🔵 Q4: Shared Libraries (Advanced)

**Problem:** Team A, B, and C each have similar pipelines (Checkout → Build → Deploy).
Copying code 3 times = maintenance nightmare.

**Solution: Jenkins Shared Libraries**
```groovy
// In every team's Jenkinsfile:
@Library('my-shared-pipeline') _
standardPipeline()    // One call runs the entire shared logic
```

**Benefits:**
- Write pipeline logic once → reuse across 100 pipelines
- Fix a bug once → all pipelines benefit
- Reduces duplication and maintenance effort

### 🎙️ Answer
> *"When multiple teams have similar CI/CD flows, I create a Jenkins Shared Library. The common logic — checkout, build, security scan, deploy — lives in a central Git repo. Each team's Jenkinsfile just calls a function from the library. This follows DRY principles and means a fix or improvement propagates to all pipelines at once."*

---

## 🔵 Q5: Multi-Language Pipelines

**Scenario:** 3-tier app: React frontend + Java backend + Python data layer.

**Solution: Docker Agents per stage**
```groovy
stage('Frontend Build') {
    agent { docker { image 'node:18' } }
    steps { sh 'npm install && npm run build' }
}
stage('Backend Build') {
    agent { docker { image 'maven:3.8-openjdk-11' } }
    steps { sh 'mvn clean package' }
}
stage('Data Layer Test') {
    agent { docker { image 'python:3.9' } }
    steps { sh 'pip install -r requirements.txt && pytest' }
}
```

> Each stage uses its own container → no language conflicts on the Jenkins server.

---

## 🔵 Q6: Jenkins Administration

| Task | How |
|---|---|
| **Backup** | Copy the hidden `.jenkins` home directory using `rsync` |
| **Auto-Scaling agents** | Configure AWS Auto Scaling Groups — add nodes on high load, remove when idle |
| **Agent communication** | **JNLP (Java Network Launch Protocol)** — agents download `agent.jar` and connect back to master |

### 🎙️ Answer: "How do you maintain Jenkins?"
> *"For backups, I use rsync to regularly copy the .jenkins home directory to S3. For scaling, I configure Jenkins with AWS Auto Scaling Groups so worker nodes spin up during high load and terminate when idle — eliminating idle cost. Agents connect to the master via JNLP — they download agent.jar and establish the connection back."*

---

## 🔵 Q7: Top 5 Jenkins Plugins to Know

| Plugin | Why It Matters |
|---|---|
| **Git** | Core — connects to all Git repositories |
| **Docker Pipeline** | Enables Docker agent strategy |
| **SonarQube Scanner** | Code quality gate integration |
| **Blue Ocean** | Visual pipeline UI (great for demos) |
| **Credentials Binding** | Injects secrets safely into pipelines |
