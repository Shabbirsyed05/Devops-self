# ☸️ Day 31: Kubernetes Architecture

**Goal:** Understand how K8s achieves Auto-Healing and Auto-Scaling through its components.

---

## 🔵 The Big Picture: Master vs Worker

```
┌─────────────────────────────────────────────────────────┐
│                   KUBERNETES CLUSTER                     │
│                                                          │
│  ┌─────────────────────┐   ┌────────────────────────┐  │
│  │   MASTER NODE       │   │   WORKER NODE(s)        │  │
│  │   (Control Plane)   │   │   (Data Plane)          │  │
│  │   = The Brain       │   │   = The Muscle          │  │
│  │                     │   │                          │  │
│  │  API Server         │   │  Kubelet                │  │
│  │  Scheduler          │   │  Container Runtime      │  │
│  │  etcd               │   │  Kube-Proxy             │  │
│  │  Controller Mgr     │   │                          │  │
│  └─────────────────────┘   └────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

---

## 🔵 Worker Node Components (Data Plane)

> The Worker Node is where your actual application (Pods) runs.

### 🔹 Kubelet — The Agent
- Runs on **every** worker node
- Acts as the "local manager" for that machine
- **Job:** Ensures Pods are running; reports crashes to the Master so auto-heal triggers
- Think of it as: *the eyes and hands of the Master on the worker*

### 🔹 Container Runtime — The Engine
- Kubelet manages the Pod, but it needs a runtime to **actually execute** the container
- **Options:** containerd, CRI-O, Docker Shim
- K8s supports any runtime following the **CRI (Container Runtime Interface)** standard

### 🔹 Kube-Proxy — The Networker
- Assigns every Pod an IP address
- Handles **networking rules** (IP tables) and simple **load balancing** between Pods
- Manages Pod-to-Pod communication within the cluster

---

## 🔵 Control Plane Components (Master Node)

> The Master Node is the brain — it makes all decisions.

### 🔸 API Server — "The Heart" (Single Entry Point)
- **Everything** in the cluster talks to the API Server first
  - Users running `kubectl` commands → API Server
  - Worker nodes reporting status → API Server
- The **only component exposed to the outside world**

### 🔸 Scheduler — "The Traffic Controller"
- **Job:** Decides *which* worker node a new Pod goes to
- Looks at available resources (CPU, RAM) across nodes and assigns accordingly

### 🔸 etcd — "The Memory"
- A **key-value store** (distributed database)
- **Job:** Stores the entire cluster state
- Example: *"There should be 3 nginx pods. Currently 2 are running. Node 2 is healthy."*
- If etcd is lost → cluster loses its memory → **backup etcd in production**

### 🔸 Controller Manager — "The Enforcer"
- Runs controllers like the **ReplicaSet Controller**
- **Job:** Constantly compares **desired state** (YAML) vs **actual state** (running)
- If they don't match (Pod died) → triggers a fix automatically

---

## 🔵 Cloud Controller Manager (CCM)

> Bridges Kubernetes and Cloud Provider APIs.

```
kubectl: "Create a Load Balancer"
       ↓
CCM: translates → AWS API: "Create an ALB"
       ↓
AWS: ✅ Load Balancer created
```

| Scenario | CCM Needed? |
|---|---|
| K8s on AWS/Azure/GCP | ✅ Yes |
| K8s on your own physical servers (on-prem) | ❌ No |

### 🎙️ Interview Answer: "Explain Kubernetes architecture"
> *"Kubernetes has two planes. The Control Plane (Master) has the API Server as the single entry point, the Scheduler which assigns Pods to nodes, etcd which stores all cluster state, and the Controller Manager which enforces desired state. The Data Plane (Worker nodes) has the Kubelet agent which runs Pods and reports health, the Container Runtime which executes containers, and Kube-Proxy which handles networking. For cloud deployments, the Cloud Controller Manager translates K8s requests into cloud provider API calls."*

# ☸️ Day 32: Managing Kubernetes Clusters & KOPS

**Goal:** Understand production-grade Kubernetes tools vs learning tools.

---

## 🔵 Dev vs Production — The Red Flag

> ⚠️ **Saying "I use Minikube in production" is an immediate red flag in interviews.**

| Tool | Environment | Why |
|---|---|---|
| **Minikube / Kind / MicroK8s** | Learning / Dev only | Single-node, no HA, not enterprise-grade |
| **KOPS / Kubeadm** | Self-managed production | Full control, more complex |
| **EKS / AKS / GKE** | Managed cloud production | AWS/Azure/Google manages the control plane |

---

## 🔵 Kubernetes Distributions

> Just like Linux has Ubuntu, CentOS, RedHat — Kubernetes has distributions.

| Distribution | By | Use Case |
|---|---|---|
| **Self-managed (KOPS)** | Open source | Full control, cost-effective |
| **OpenShift** | Red Hat | Enterprise — comes with support subscription |
| **Rancher** | SUSE | Multi-cluster management platform |
| **EKS** | AWS | Managed — AWS handles the control plane |
| **AKS** | Azure | Managed — Azure handles the control plane |
| **GKE** | Google | Managed — Google handles the control plane |

> 💡 **Why managed services?** If EKS crashes, open a support ticket with AWS. If self-managed crashes, you're on your own.

---

## 🔵 KOPS — Kubernetes Operations

> KOPS automates creating and managing production-grade K8s clusters on AWS.

**KOPS vs KubeADM:**

| | KOPS | KubeADM |
|---|---|---|
| **Setup** | Automated | Manual and complex |
| **Provisions** | EC2, Auto Scaling Groups, Load Balancers | Just the K8s components |
| **Best for** | AWS-based self-managed clusters | Any infrastructure |

**KOPS Workflow:**
```bash
# 1. Create S3 bucket (stores cluster config = "state store")
aws s3 mb s3://kops-state-bucket

# 2. Create cluster config
kops create cluster \
  --name=mycluster.k8s.local \
  --state=s3://kops-state-bucket \
  --node-count=2 \
  --node-size=t2.micro \
  --zones=us-east-1a

# 3. Actually create the AWS resources
kops update cluster --name=mycluster.k8s.local --yes

# 4. Validate cluster is ready
kops validate cluster
```

> ⚠️ **KOPS creates real AWS resources (EC2, EBS, ELB) — costs money. Use Minikube for daily practice.**

### 🎙️ Interview Answer: "How do you manage Kubernetes in production?"
> *"In production, we use either managed services like EKS or self-managed clusters with KOPS on AWS. KOPS automates provisioning EC2 instances, Auto Scaling Groups, and Load Balancers — unlike KubeADM which is manual. The cluster state is stored in S3, and KOPS handles upgrades and lifecycle management. For learning and dev environments, Minikube is sufficient, but it's never used in production."*

# ☸️ Day 33: Kubernetes Pods & Deploy Your First App

**Goal:** Understand Pods — the fundamental unit of Kubernetes — and deploy your first app.

---

## 🔵 What is a Pod?

> In Docker you deploy **Containers**. In Kubernetes you deploy **Pods**.

```
┌─────────────────────────────────┐
│           POD                   │
│  ┌────────────┐                 │
│  │ Container  │  ← your app     │
│  └────────────┘                 │
│  Shared Network + Storage       │
└─────────────────────────────────┘
```

**Why Pods instead of raw containers?**

| Docker | Kubernetes Pod |
|---|---|
| Long CLI flags (`-p`, `-v`, `--network`) | Clean YAML spec — no memorizing flags |
| One container per command | Can have multiple containers sharing network/storage |

**Multi-container Pod example:**
```
Pod
├── Main App Container        (app logic)
└── Sidecar Container         (e.g., log collector, proxy)
     → Both share localhost + volume
```

---

## 🔵 The Two Tools: Minikube + kubectl

| Tool | Purpose |
|---|---|
| **Minikube** | Creates a single-node K8s cluster inside a VM on your laptop |
| **kubectl** | CLI to send commands to the cluster (talks to the API Server) |

> Minikube = the cluster | kubectl = the remote control

---

## 🔵 Imperative vs Declarative

| Approach | How | Example |
|---|---|---|
| **Imperative** (Docker way) | Type long commands | `docker run -p 80:80 -v /data:/app nginx` |
| **Declarative** (K8s way) | Write a YAML file | `kubectl apply -f pod.yaml` |

> ✅ K8s YAML is declarative — you describe *what you want*, K8s figures out *how to do it*.

---

## 🔵 Sample Pod YAML

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:latest
      ports:
        - containerPort: 80
```

---

## 🔵 Deploy & Debug Commands

```bash
# Deploy
kubectl create -f pod.yaml       # Create from file
kubectl apply -f pod.yaml        # Create or update from file

# Verify
kubectl get pods                 # List all pods + status
kubectl get pods -o wide         # Show pod IP and node

# Debug
kubectl describe pod nginx-pod   # Full details — why is it pending/crashing?
kubectl logs nginx-pod           # App logs (stdout) — syntax errors, crashes

# Access
minikube ssh                     # Enter the cluster VM
curl <pod-ip>                    # Hit the pod's internal IP
```

**Common error messages in `kubectl describe`:**

| Error | Meaning |
|---|---|
| `ImagePullBackOff` | Can't download the container image — check image name/registry |
| `CrashLoopBackOff` | Container keeps crashing — check `kubectl logs` |
| `Pending` | No node has enough resources to schedule the Pod |

---

## 🔵 The Key Limitation of Pods

> **If you delete a Pod — it's gone forever.** It doesn't restart itself.

```bash
kubectl delete pod nginx-pod   # Pod is gone, nothing brings it back
```

This is why in production we **never deploy raw Pods** — we use **Deployments** (Day 34).

### 🎙️ Interview Answer: "What is a Pod in Kubernetes?"
> *"A Pod is the smallest deployable unit in Kubernetes — it's a wrapper around one or more containers that share the same network namespace and storage volumes. Unlike Docker where you pass long flags to `docker run`, in K8s you define a Pod's spec in a YAML file and apply it declaratively. The key limitation of Pods is that they don't self-heal — if deleted they're gone. That's why production workloads use Deployments, which manage Pods and ensure they're always running."*

# ☸️ Day 34: Kubernetes Deployments & ReplicaSets

**Goal:** Solve the Pod limitation — make applications self-healing and scalable.

---

## 🔵 The Key Interview Question: Container vs Pod vs Deployment

| Object | What It Is | What It Adds |
|---|---|---|
| **Container** | App code + dependencies packaged together | Nothing yet — just the package |
| **Pod** | Wrapper around container(s) | Shared network + storage for containers |
| **Deployment** | Wrapper around Pod(s) | **Auto-Healing + Auto-Scaling** |

---

## 🔵 The Hierarchy: How They Work Together

```
You create a Deployment
        ↓
Deployment creates a ReplicaSet
        ↓
ReplicaSet creates and manages Pods
        ↓
Pods run Containers
```

> You manage the **Deployment**. The Deployment manages everything below it automatically.

---

## 🔵 What is a ReplicaSet?

> A **controller** that ensures the desired number of Pods is always running.

```yaml
# Deployment YAML
replicas: 3    # "I want 3 pods always running"
```

```
ReplicaSet enforcing replicas: 3
├── Pod-1 ✅ Running
├── Pod-2 ✅ Running
└── Pod-3 ✅ Running

Pod-2 gets deleted →
ReplicaSet detects: actual=2, desired=3
ReplicaSet creates → Pod-4 ✅ (before Pod-2 even finishes terminating)
```

**This is Auto-Healing in action.**

---

## 🔵 Sample Deployment YAML

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:latest
          ports:
            - containerPort: 80
```

---

## 🔵 Scaling Up (Zero Downtime)

```bash
# Edit replicas in YAML: replicas: 1 → replicas: 3
kubectl apply -f deployment.yaml

# ReplicaSet spins up 2 more Pods automatically
```

Or scale directly:
```bash
kubectl scale deployment nginx-deployment --replicas=5
```

---

## 🔵 Key Commands

```bash
kubectl get all                          # See everything: pods, deploy, rs, svc
kubectl get deploy                       # Check deployment status
kubectl get rs                           # Check ReplicaSet (created automatically)
kubectl get pods -w                      # Watch pods in real-time (-w = watch)
kubectl delete pod <pod-name>            # Delete a pod — ReplicaSet replaces it
kubectl rollout status deployment/nginx  # Check rollout progress
```

### 🎙️ Interview Answer: "What is a Deployment in Kubernetes?"
> *"A Deployment is a higher-level K8s object that manages Pods through a ReplicaSet. When I define `replicas: 3`, the ReplicaSet ensures exactly 3 Pods are always running. If one crashes or gets deleted, the ReplicaSet creates a replacement before the old one even finishes terminating — achieving zero-downtime auto-healing. Deployments also handle rolling updates so you can update an image version with no service interruption."*

### 🎙️ Interview Answer: "ReplicaSet vs Deployment?"
> *"A ReplicaSet is the controller that ensures the right number of Pods are running. A Deployment is a wrapper around the ReplicaSet that also manages rolling updates and rollbacks. In practice, you never create ReplicaSets directly — you create Deployments and they manage ReplicaSets for you."*

# ☸️ Day 35: Kubernetes Services

**Goal:** Solve the networking problem — stable access to Pods that constantly change IPs.

---

## 🔵 The Problem: IP Churn

```
Pod dies → new Pod created (Auto-Heal) → NEW IP ADDRESS

User was connecting to: 172.16.3.4  ← now dead
New pod IP:             172.16.3.8  ← user doesn't know this
Result: Connection fails ❌
```

> You can't ask users or other services to constantly update which IP they're talking to.

---

## 🔵 The Solution: Kubernetes Service

> A **Service** provides a **stable IP and DNS name** that never changes — even when backend Pods change.

```
User → Service (stable IP: 10.0.0.50) → Pod-1 (172.16.3.4)
                                       → Pod-2 (172.16.3.5)
                                       → Pod-3 (172.16.3.6)

Pod-2 dies and is replaced →
Service → Pod-1, Pod-3, Pod-4 (new)  (automatically discovered via labels)
```

**A Service solves 3 problems simultaneously:**

---

## 🔵 Problem 1: Load Balancing

```
30 requests → Service → 10 to Pod-A
                       → 10 to Pod-B
                       → 10 to Pod-C
```

> Service distributes traffic evenly across all healthy Pods.

---

## 🔵 Problem 2: Service Discovery (Labels & Selectors)

> Services don't track Pod IPs — they track **Labels**.

```yaml
# Pod has this label:
labels:
  app: payment

# Service selects using:
selector:
  app: payment
```

```
Pod dies (IP: 172.16.3.4) → new Pod created (IP: 172.16.3.8)
New Pod has label: app: payment
Service auto-discovers it → traffic resumes ✅
```

> No matter how many times a Pod dies and restarts with a new IP — as long as it has the right label, the Service finds it.

---

## 🔵 Problem 3: External Exposure — The 3 Service Types

> **Most important interview question in this section.**

| Type | Scope | Use Case | Example |
|---|---|---|---|
| **ClusterIP** (default) | Internal cluster only | Backend services, databases | Payment service talking to DB |
| **NodePort** | Organization / VPN level | Expose on worker node's port | Internal tools for employees |
| **LoadBalancer** | Public internet | Customer-facing apps | amazon.com, netflix.com |

### ClusterIP
```
Internet → ❌ blocked
Internal K8s app → ✅ can reach service
```
```yaml
spec:
  type: ClusterIP   # (this is the default if you don't specify)
```

### NodePort
```
Internet → Worker Node IP:30080 → Service → Pods
```
```yaml
spec:
  type: NodePort
  ports:
    - port: 80
      nodePort: 30080   # Must be 30000-32767
```

### LoadBalancer
```
Internet → AWS ALB (public IP) → Service → Pods
```
```yaml
spec:
  type: LoadBalancer
  # Triggers Cloud Controller Manager → creates AWS Load Balancer
```

---

## 🔵 Service YAML Example

```yaml
apiVersion: v1
kind: Service
metadata:
  name: payment-service
spec:
  selector:
    app: payment          # Finds all pods with label app=payment
  ports:
    - port: 80            # Service port (what clients connect to)
      targetPort: 8080    # Pod port (where app actually runs)
  type: LoadBalancer      # Expose to internet via cloud LB
```

---

## 🔵 Key Commands

```bash
kubectl get svc                          # List all services
kubectl describe svc payment-service     # See selector, endpoints, type
kubectl get endpoints                    # See which pod IPs the service is routing to
```

### 🎙️ Interview Answer: "What is a Kubernetes Service?"
> *"A Kubernetes Service provides a stable IP and DNS name for a set of Pods. Since Pods get new IPs every time they restart, the Service acts as a permanent middleman. It uses Labels and Selectors to discover Pods — not IPs — so it automatically picks up new Pods. Services also do load balancing across replicas. There are three types: ClusterIP for internal-only access, NodePort for organizational/VPN-level access, and LoadBalancer which provisions a cloud load balancer for public internet access."*

### 🎙️ Interview Answer: "ClusterIP vs NodePort vs LoadBalancer?"
> *"ClusterIP is the default — only accessible inside the cluster, good for databases and internal services. NodePort exposes the app on a specific port of each worker node, making it accessible to anyone who can reach the node's IP — useful for internal company tools. LoadBalancer talks to the cloud provider to create a public IP — this is what you use for customer-facing applications like a website."*

|---|---|
