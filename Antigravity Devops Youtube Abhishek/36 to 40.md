# 🎯 Day 36: Kubernetes Interview Questions — Part 1

**Goal:** Mock interview covering Days 30–35 concepts. 10 scenario-based questions.

---

## 🔵 Q1: Docker vs Kubernetes?

| | Docker | Kubernetes |
|---|---|---|
| **Type** | Container Platform (single node) | Container Orchestration Platform (cluster) |
| **Failure** | Node dies → app dies | Node dies → workload moves to healthy node |
| **Scaling** | Manual | Auto-Scaling (HPA) |
| **Healing** | None | Auto-Healing (ReplicaSet) |

### 🎙️ Answer
> *"Docker is a container platform for building and running containers on a single machine. Kubernetes is an orchestration platform that manages containers across a cluster. The key advantages of K8s over Docker alone are auto-healing — failed pods are automatically replaced — and auto-scaling, which handles traffic spikes automatically."*

---

## 🔵 Q2: Docker Swarm vs Kubernetes?

| | Docker Swarm | Kubernetes |
|---|---|---|
| **Setup** | Simple, easy | Complex, powerful |
| **Scale** | Small teams | Enterprise / Large Scale |
| **Ecosystem** | Limited | Vast CNCF integrations, CRDs |
| **Industry adoption** | Declining | Industry standard |

### 🎙️ Answer
> *"Swarm is simpler to set up but limited at scale. Kubernetes is the industry standard for enterprise workloads — it supports advanced networking, Custom Resource Definitions, and integrates with the entire CNCF ecosystem. In production, Kubernetes is always preferred."*

---

## 🔵 Q3: Container vs Pod?

> *"A Pod is a wrapper around one or more containers. Containers in the same Pod share the same network (localhost) and storage volumes. This enables patterns like sidecars — a main app container plus a helper container for logging or proxying."*

---

## 🔵 Q4: Control Plane vs Data Plane?

| Control Plane (Master) | Data Plane (Worker) |
|---|---|
| API Server — entry point for all commands | Kubelet — agent, monitors pods, triggers auto-heal |
| Scheduler — assigns pods to nodes | Kube-Proxy — networking rules, load balancing |
| etcd — cluster state store (key-value) | Container Runtime — runs containers (containerd, CRI-O) |
| Controller Manager — enforces desired state | |
| Cloud Controller Manager — cloud API bridge | |

---

## 🔵 Q5: What is a Namespace?

> *"A Namespace provides logical isolation within a single cluster. Instead of creating 20 clusters for 20 teams, you create one cluster with 20 namespaces. Team A cannot accidentally access or delete Team B's resources. It's a cost-efficient way to multi-tenant a cluster."*

---

## 🔵 Q6: Service Types?

| Type | Scope | Use Case |
|---|---|---|
| **ClusterIP** | Internal only | Databases, internal microservices |
| **NodePort** | Organization/VPN | Internal tools accessible to employees |
| **LoadBalancer** | Public internet | Customer-facing websites |

---

## 🔵 Q7: Day-to-Day Activities as a DevOps Engineer?

> ⚠️ **Don't say "I just run commands."**

### 🎙️ Full Answer
> *"My day-to-day involves three main areas. First, cluster management — handling upgrades, security patches, and scaling worker nodes. Second, acting as a subject matter expert for developers — helping them troubleshoot why pods are in CrashLoopBackOff or why traffic isn't routing correctly to their services. Third, monitoring — ensuring the cluster is healthy, reviewing dashboards, and setting up alerts for anomalies like high CPU or pod restarts."*

# 🌐 Day 37: Kubernetes Services Deep Dive

**Goal:** See how Services actually work with a real app, visualize load balancing.

---

## 🔵 The IP Churn Problem (Demonstrated)

```
Deployment with 2 replicas:
Pod-1: 172.16.0.5 ✅
Pod-2: 172.16.0.7 ✅

Delete Pod-1 → ReplicaSet creates Pod-3: 172.16.0.9
User was connected to 172.16.0.5 → now unreachable ❌
```

**Proof that you need a Service with a stable IP.**

---

## 🔵 Service Discovery: Labels Are the Key

> Services don't track Pod IPs — they track **Labels**.

```yaml
# Pod YAML
labels:
  app: payment     # ← Pod tagged

# Service YAML
selector:
  app: payment     # ← Service finds pods by this label
```

**What happens if label doesn't match?**
```
Service selector: app: payments   (typo!)
Pod label:        app: payment
Result: 0 endpoints — Service can't reach any pod ❌
```

> 🎙️ *"Always verify that Service selectors exactly match Pod labels — this is the #1 cause of connectivity issues in Kubernetes."*

---

## 🔵 NodePort vs LoadBalancer (Practical)

| | NodePort | LoadBalancer |
|---|---|---|
| **Access** | `<node-ip>:30007` | Public cloud IP |
| **On Minikube** | Works ✅ | Shows "Pending" ❌ (no cloud CCM) |
| **Production** | Internal/VPN tools | Public websites |

---

## 🔵 Load Balancing Visualized (Kubeshark)

**Test:** Send 6 curl requests to the Service endpoint.

**Result (Round Robin):**
```
Request 1 → Pod-A (172.16.0.5)
Request 2 → Pod-B (172.16.0.7)
Request 3 → Pod-A (172.16.0.5)
Request 4 → Pod-B (172.16.0.7)
...
```

> Proves Service distributes load automatically — no manual configuration needed.

**Kubeshark** = network traffic visualizer for Kubernetes (like Wireshark for K8s).

# 🔀 Day 38: Kubernetes Ingress

**Goal:** Understand why Ingress replaces LoadBalancer services for production routing.

---

## 🔵 The Problem with LoadBalancer Services

```
App 1 (payment)  → LoadBalancer → Public IP: 3.4.5.6   (costs $$$)
App 2 (login)    → LoadBalancer → Public IP: 3.4.5.7   (costs $$$)
App 3 (catalog)  → LoadBalancer → Public IP: 3.4.5.8   (costs $$$)
```

> Each LoadBalancer = one cloud load balancer = **separate cost**. Not scalable.

---

## 🔵 The Solution: Ingress

> **One** Ingress (one Load Balancer) → routes to **many** services based on rules.

```
Internet → Ingress (single LB) ─┬─ /payment → Payment Service
                                 ├─ /login   → Login Service
                                 └─ /catalog → Catalog Service
```

**Two types of routing:**

| Routing Type | Example | Target |
|---|---|---|
| **Path-based** | `example.com/payment` | Payment Service |
| **Host-based** | `amazon.com` vs `amazon.in` | Different apps |

**TLS termination:** Ingress can manage HTTPS certificates — internal pods don't need SSL.

---

## 🔵 How to Set Up Ingress (Minikube)

```bash
# Step 1: Enable Nginx Ingress Controller
minikube addons enable ingress

# Step 2: Create Ingress resource
kubectl apply -f ingress.yaml

# Step 3: Local DNS trick (no real domain needed)
# Edit /etc/hosts:
# <minikube-ip>  foo.bar.com
```

**Sample Ingress YAML:**
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
spec:
  rules:
    - host: foo.bar.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: my-service
                port:
                  number: 80
```

### 🎙️ Interview Answer: "LoadBalancer vs Ingress?"
> *"A LoadBalancer service creates one cloud load balancer per service — expensive at scale. Ingress uses a single load balancer (the Ingress Controller) and routes traffic to multiple services based on hostname or URL path rules. It also handles TLS termination centrally, so internal services don't need to manage certificates."*

# 🔐 Day 39: Kubernetes RBAC

**Goal:** Control who can access the cluster and what they're allowed to do.

---

## 🔵 What is RBAC?

> **Role-Based Access Control** — decides *who* can access the cluster and *what* they can do.

**Why critical?**
- Without RBAC, every cluster user may have full admin access
- A developer could accidentally delete a production database
- A compromised Pod could destroy the API Server

---

## 🔵 The "User" Mystery — Top Interview Question

**Question:** *"How do you create a user in Kubernetes?"*

**Answer:** You **can't**. Kubernetes **does not manage users natively**.

```
Kubernetes offloads user management to External Identity Providers:
├── AWS IAM (for EKS)
├── Google Identity (for GKE)
├── LDAP / Active Directory
└── Okta
```

> *"The API Server acts like an OAuth server — it trusts external identity providers to verify who the user is."*

---

## 🔵 The 3 Pillars of RBAC

| Component | What It Is | Analogy |
|---|---|---|
| **User / ServiceAccount** | The entity requesting access | 👤 Person |
| **Role** | YAML defining permissions (get, list, delete pods) | 🪪 ID Badge listing what you can do |
| **RoleBinding** | Connects a User to a Role | 🎟️ Handing the badge to the person |

> ⚠️ **Without RoleBinding, permissions don't apply** — Role alone does nothing.

---

## 🔵 Role vs ClusterRole

| | Role | ClusterRole |
|---|---|---|
| **Scope** | Single Namespace | Entire Cluster |
| **Use case** | Dev team access to their namespace | Admin access across all namespaces |

---

## 🔵 Service Accounts for Pods

```
Every Pod automatically gets a "default" Service Account
       ↓
Hacker compromises Pod → inherits all its Service Account permissions ❌
```

**Best Practice:**
- Create custom Service Accounts with minimal permissions
- Example: Restrict pods from reading Secrets they don't need

---

## 🔵 Practice Environment: OpenShift Sandbox

> Free 30-day Red Hat OpenShift cluster — **better than Minikube for security practice**.

| Feature | Minikube | OpenShift Sandbox |
|---|---|---|
| Cost | Free | Free (30 days) |
| RBAC | Minimal | Production-like restrictions |
| Best for | Learning K8s basics | Practicing security & RBAC |

### 🎙️ Interview Answer: "What is RBAC in Kubernetes?"
> *"RBAC is Kubernetes's access control system. It uses three components: a Role that defines what actions are allowed (like get, list, or delete pods), a Subject which is the user or service account requesting access, and a RoleBinding that connects the two. Kubernetes doesn't manage users itself — it integrates with external identity providers like AWS IAM or LDAP. For pods, I always create custom Service Accounts with least-privilege permissions instead of using the default service account."*

# 🧩 Day 40: Custom Resources & Custom Controllers

**Goal:** Understand how tools like Istio and ArgoCD extend Kubernetes.

---

## 🔵 Why Native Resources Aren't Enough

```
Native K8s knows: Pod, Deployment, Service, Ingress
It does NOT know: VirtualService (Istio), Application (ArgoCD), Policy (Kyverno)
```

> Kubernetes core developers can't add logic for every tool — K8s would be unmaintainable.

**Solution:** Kubernetes allows you to **extend its API** with Custom Resources.

---

## 🔵 The 3-Part Custom Resource Trinity

```
CRD (Definition) + CR (Instance) + Custom Controller (Brain)
     = New Kubernetes capability
```

### 🧾 A. CRD — Custom Resource Definition ("The Rulebook")

> Tells Kubernetes: *"I am introducing a new object type called VirtualService."*

- Defines schema, fields, and validation rules
- Analogy: **Adding a new word to the Kubernetes dictionary**

```bash
kubectl get crd    # See all CRDs installed in the cluster
```

---

### 📄 B. CR — Custom Resource ("The Request")

> The actual YAML created by a developer to *use* the new feature.

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService          # Custom kind defined by CRD
metadata:
  name: my-route
spec:
  ...
```

Kubernetes validates the CR against the CRD schema when applied.

---

### 🧠 C. Custom Controller ("The Brain")

> A program (usually Golang) running as a Pod that watches for CRs and acts on them.

```
CR created: "VirtualService for payment traffic"
      ↓
Custom Controller detects it
      ↓
Controller configures actual network routing rules
```

> ⚠️ **CRD + CR without a Controller = nothing happens.** The resource just sits there.

---

## 🔵 Native vs Custom: Side-by-Side

| | Native K8s | Custom (e.g., Istio) |
|---|---|---|
| **Definition** | Deployment (built-in) | CRD |
| **Instance** | deployment.yaml | virtual-service.yaml |
| **Brain** | Deployment Controller | Istiod (Custom Controller) |
| **Action** | Creates pods | Configures traffic mesh |

---

## 🔵 DevOps Engineer's Role

| Role | Responsibility |
|---|---|
| **DevOps Engineer** | Install CRDs + Controllers (via Helm), ensure controllers are healthy, debug issues |
| **Developer** | Write Custom Resource YAMLs to use the feature |

### 🎙️ Interview Answer: "What are CRDs in Kubernetes?"
> *"CRDs — Custom Resource Definitions — allow you to extend the Kubernetes API with new object types. For example, Istio adds VirtualService as a new kind. A CRD defines the schema, a Custom Resource is an instance of that schema, and a Custom Controller is the program that watches for those resources and takes action. If a developer tells me their Istio setup isn't working, I check whether the custom controller is running and review its logs — that's usually where the problem is."*

# 🔑 Day 41: ConfigMaps & Secrets

**Goal:** Separate configuration from code — the right way.

---

## 🔵 The Problem: Hardcoding

```python
# app.py
DB_HOST = "prod-db.company.com"   # ❌ hardcoded
DB_PASS = "supersecret123"         # ❌ hardcoded
```

**Problems:**
- Any config change → rebuild entire Docker image
- Passwords exposed to anyone with code access

---

## 🔵 The Solution: ConfigMap vs Secret

| | ConfigMap | Secret |
|---|---|---|
| **Data type** | Non-sensitive (ports, URLs, hostnames) | Sensitive (passwords, API keys, tokens) |
| **Storage** | Plain text | Encrypted at rest in etcd |
| **CLI display** | Plaintext | Base64-encoded |
| **Access** | Open to developers | Restricted via RBAC |

> 📌 **Base64 is encoding, NOT encryption.** Anyone can decode it: `echo <value> | base64 --decode`
> That's why RBAC on Secrets is mandatory.

---

## 🔵 Two Injection Methods

### Method 1: Environment Variables
```yaml
env:
  - name: DB_PORT
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: DB_PORT
```
- ❌ **Does NOT auto-update** — pod must restart to pick up new values

### Method 2: Volume Mounts ⭐ (Recommended)
```yaml
volumes:
  - name: config-volume
    configMap:
      name: app-config
volumeMounts:
  - name: config-volume
    mountPath: /opt/config
```
- ✅ **Auto-updates** — file changes when ConfigMap changes (no pod restart needed)
- Requires app to re-read the file dynamically

---

## 🔵 Quick Commands

```bash
# Create ConfigMap
kubectl create configmap app-config --from-literal=DB_PORT=3306

# Create Secret
kubectl create secret generic db-secret --from-literal=DB_PASS=secret123

# Decode a Secret
kubectl get secret db-secret -o jsonpath='{.data.DB_PASS}' | base64 --decode

# View ConfigMap
kubectl get configmap app-config -o yaml
```

### 🎙️ Interview Answer: "ConfigMap vs Secret?"
> *"ConfigMaps store non-sensitive configuration like ports, hostnames, and URLs in plain text. Secrets store sensitive data like passwords and API keys — they're encrypted at rest in etcd and access is restricted via RBAC. I prefer Volume Mounts over environment variables for injecting both, because volume mounts auto-update when the ConfigMap or Secret changes without requiring a pod restart."*

# 📊 Day 42: Kubernetes Monitoring — Prometheus & Grafana

**Goal:** Set up observability for your cluster using the industry-standard monitoring stack.

---

## 🔵 The Power Duo

```
Prometheus (Brain + Storage) ←→ Grafana (Visualization)
```

| Tool | Role |
|---|---|
| **Prometheus** | Scrapes metrics, stores in Time Series DB, triggers alerts |
| **Grafana** | Connects to Prometheus, displays dashboards — does NOT store data |

---

## 🔵 Prometheus Architecture (Pull Model)

```
Kubernetes API Server → exposes /metrics endpoint
       ↓
Prometheus scrapes /metrics every N seconds
       ↓
Stores in internal TSDB
       ↓
Metric crosses threshold → Alert Manager → Slack / Email / PagerDuty
```

> Prometheus uses a **Pull mechanism** — it goes to fetch metrics (not pushed to it).

---

## 🔵 Kube-State-Metrics — Key Interview Topic

> The default K8s API metrics endpoint gives only **basic health data**. Not enough for real observability.

**Kube-State-Metrics adds:**
- Desired vs actual replica counts
- Pod restart counts
- Deployment / StatefulSet health
- Resource request vs limit usage

> ⚠️ **Without Kube-State-Metrics, Grafana dashboards will look almost empty.**

---

## 🔵 Installation with Helm (The Easy Way)

```bash
# Add repos
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo add grafana https://grafana.github.io/helm-charts

# Install
helm install prometheus prometheus-community/prometheus
helm install grafana grafana/grafana
```

Helm auto-installs: Service Accounts, ConfigMaps, Services, all dependencies.

---

## 🔵 Grafana Setup Workflow

```bash
# Step 1: Expose Grafana
kubectl patch svc grafana -p '{"spec":{"type":"NodePort"}}'

# Step 2: Login to Grafana UI, add Prometheus as data source

# Step 3: Import community dashboard
Dashboard ID: 3662   # Standard K8s cluster overview dashboard
```

**Dashboard 3662 shows:** CPU, Memory, Network I/O, Pod uptime — automatically.

---

## 🔵 Monitoring Your Own App

```
Developer adds Prometheus client library to app
       ↓
App exposes /metrics endpoint
       ↓
Update Prometheus ConfigMap with new scrape target
       ↓
Prometheus scrapes custom app metrics
       ↓
Display in Grafana alongside cluster metrics
```

### 🎙️ Interview Answer: "How do you monitor Kubernetes?"
> *"We use Prometheus and Grafana. Prometheus scrapes metrics from the Kubernetes API and from Kube-State-Metrics, which gives us deep data like replica counts and pod restart counts. Alert Manager sends notifications to Slack when thresholds are breached. Grafana connects to Prometheus and displays dashboards — we use community dashboard 3662 as a starting point. We also instrument our own applications with Prometheus client libraries so custom metrics appear alongside cluster metrics."*

# 🌐 Day 43: AWS Live Project — Deploy App Using HTTPD

**Goal:** End-to-end project — take HTML/CSS from local → GitHub → EC2 → live on internet.

---

## 🔵 The Full Deployment Flow

```
Local code → Git commit → GitHub → EC2 clone → Apache (HTTPD) → Public IP → Live!
```

---

## Phase 1: Source Code Management

```bash
git init
git add .
git commit -m "Initial website"
git push origin main    # Push to GitHub repo "AWS-demo"
```

> **Why GitHub before EC2?** You can't drag-and-drop files to a cloud server. Servers pull from repos.

---

## Phase 2: Launch EC2 Instance

| Setting | Value |
|---|---|
| **OS** | Red Hat Linux (Free Tier eligible) |
| **Instance Type** | t2.micro (1 vCPU, 1GB RAM) |
| **Key Pair** | Create `demo-website.pem` — download it |
| **Public IP** | ✅ Must enable auto-assign |
| **Security Group** | Allow SSH (22) + HTTP (80) |

> ⚠️ **If Port 80 is not open in Security Group, the website won't load.**

---

## Phase 3: Connect to EC2

```bash
# Fix key permissions
chmod 400 demo-website.pem

# SSH in
ssh -i demo-website.pem ec2-user@<Public-IP>
```

---

## Phase 4: Configure & Deploy

```bash
# Switch to root
sudo su -

# Update system + install Git
yum update -y
yum install git -y

# Clone your website code
git clone <your-github-repo-url>

# Install Apache web server
yum install httpd -y

# Move website files to Apache's web root
cp -r <cloned-folder>/* /var/www/html/

# Start Apache
systemctl start httpd
```

---

## Phase 5: Access the Website

```
Browser → http://<EC2-Public-IP>
```

> ⚠️ **Common mistake:** Browser defaults to `https://` — use `http://` since SSL is not configured.

**Result:** Static website live on the public internet! ✅

---

## 🔵 Key Concepts Reinforced

| Concept | What It Reinforced |
|---|---|
| **Git → GitHub** | Central source of truth for deployment |
| **Security Groups** | Must open Port 80 for HTTP traffic |
| **chmod 400** | AWS rejects keys with open permissions |
| **`/var/www/html`** | Apache's web root — files here are served |
| **`systemctl start httpd`** | Start the web server service |

### 🎙️ Interview Answer: "How would you deploy a static website to AWS?"
> *"I'd push the code to GitHub first — you can't manually transfer files to a cloud server. Then I'd launch an EC2 instance with Red Hat or Ubuntu, open Port 22 for SSH and Port 80 for HTTP in the Security Group. After SSHing in with the .pem key, I'd install Git and Apache (httpd), clone the repo, copy files to `/var/www/html`, and start the httpd service. The site is then accessible via the EC2 Public IP."*
