# 🧱 Day 16: Infrastructure as Code (IaC) & Terraform — Theory

**Goal:** Understand *why* Terraform was created and how it solves the multi-cloud problem.

---

## 🔵 The Problem: The "Language" Barrier

Imagine you're a DevOps engineer at Flipkart automating infrastructure on AWS using **CloudFormation (CFT)**.

### Scenario A — Migration
> Management says: *"Move everything to Azure to save costs."*
- Your CloudFormation scripts are **completely useless on Azure**
- You must rewrite everything in **ARM (Azure Resource Manager)**

### Scenario B — Hybrid Cloud
> Company decides: *"Use AWS for S3 storage, Azure for DevOps pipelines."*
- You must **master two completely different tools simultaneously**

---

## 🔵 The Solution: Terraform

> **One tool. Any cloud.**

| Tool | Cloud | Problem |
|---|---|---|
| **CloudFormation (CFT)** | AWS only | Useless on Azure/GCP |
| **Azure Resource Manager (ARM)** | Azure only | Useless on AWS/GCP |
| **Heat Templates** | OpenStack only | Useless on public clouds |
| **Terraform** ⭐ | All clouds | Works everywhere — same syntax |

**How it works:**
```
Your Terraform code → Terraform translates → Cloud-specific API call → Resource created
```

If you migrate from AWS to Azure, you **don't learn a new language** — you just update the **"Provider"** block.

---

## 🔵 Key Concept: "API as Code"

| Method | What Happens |
|---|---|
| **Browser (UI)** | You click buttons on google.com — uses a visual interface |
| **Script (API)** | Your code talks to Google's API programmatically — no browser |

**Terraform's role:**
- Every cloud provider exposes APIs to create resources
- Instead of you writing complex Python/Shell scripts to call these APIs, you write simple Terraform config files
- Terraform handles the API translation for you

```
You write:  "create EC2"
Terraform:  POST https://ec2.amazonaws.com/... (complex API call)
AWS:        ✅ EC2 created
```

### 🎙️ Interview Answer: "What is Terraform and why use it?"
> *"Terraform is an open-source Infrastructure as Code tool by HashiCorp. It solves the multi-cloud problem — instead of learning CloudFormation for AWS, ARM for Azure, and Heat Templates for OpenStack, I write one Terraform configuration and it translates my code into the specific API calls each cloud provider understands. This is especially valuable in hybrid cloud environments."*

# 🧱 Day 17: Terraform In-Depth & Production Setup

**Goal:** Understand the Terraform lifecycle, state file, and production-grade setup.

---

## 🔵 The 4 Terraform Commands (The Lifecycle)

```
init → plan → apply → destroy
```

| Command | What It Does | When to Use |
|---|---|---|
| `terraform init` | Downloads plugins/providers needed to talk to AWS | First time, or when providers change |
| `terraform plan` | **Dry run** — shows what WILL be created/deleted | Always run before apply |
| `terraform apply` | Actually creates the infrastructure | After reviewing the plan |
| `terraform destroy` | Deletes all tracked resources | Cleanup / teardown |

> ⚠️ **Always run `terraform plan` before `terraform apply`** — it prevents accidental deletions.

```bash
terraform init
terraform plan        # Review changes — nothing is created yet
terraform apply       # Confirm → resources are created
terraform destroy     # Deletes everything Terraform created
```

---

## 🔵 The Most Critical Concept: The State File

> `terraform.tfstate` — the **heart** of Terraform

**What it does:** Maps your Terraform code to real-world cloud resources.
```
main.tf:  resource "aws_instance" "web" { ... }
            ↕  tracked in state file
AWS:      EC2 Instance ID: i-0abc123def456
```

### ⚠️ State File Problems

| Problem | Detail |
|---|---|
| **Contains secrets** | Sensitive data (API keys, passwords) stored in plaintext |
| **Can't be Git-merged** | Standard Git merge breaks state files |
| **Can't live on laptop** | If your laptop dies, team loses track of all infrastructure |

> **Rule #1:** Never store `terraform.tfstate` on your local machine or in Git.

---

## 🔵 Production Setup: Remote Backend + Locking

> This is the **standard interview answer** for *"How do you set up Terraform in production?"*

```
┌──────────────────────────────────────────────────┐
│              Terraform Remote Backend             │
│                                                   │
│  S3 Bucket  ←  stores state file (shared truth)  │
│  DynamoDB   ←  locks state during apply           │
└──────────────────────────────────────────────────┘
```

| Component | Purpose |
|---|---|
| **S3 Bucket** | Stores the state file centrally — team shares one source of truth |
| **DynamoDB Table** | Locks the state file — prevents two engineers running `apply` simultaneously |

**Why DynamoDB locking matters:**
> Two engineers run `terraform apply` at the same time → both modify the same infrastructure → **state corruption and resource conflicts**.
> DynamoDB prevents this: only one apply can run at a time.

---

## 🔵 Code Structure Best Practices

> Don't put everything in one file — split into purpose-driven files:

```
project/
├── main.tf          # Resource logic (EC2, VPC, S3)
├── variables.tf     # Input variables (instance_type, region)
├── outputs.tf       # What to display after deploy (public IP)
└── modules/         # Reusable code blocks
```

| File | Purpose | Example |
|---|---|---|
| `main.tf` | Defines the actual resources | EC2, VPC, RDS |
| `variables.tf` | Input variables — no hardcoding | `instance_type = "t2.micro"` |
| `outputs.tf` | Shows useful info after apply | Prints the public IP |
| **Modules** | Reusable blocks across environments | Same "web server" used in Dev, Stage, Prod |

---

## 🔵 Limitations of Terraform (Interview Prep)

| Limitation | Detail |
|---|---|
| **State Drift** | If someone manually changes a resource in the AWS Console, Terraform doesn't know — state file becomes out of sync |
| **Not GitOps-Friendly** | State file complexity makes it harder to use with GitOps tools like ArgoCD vs Kubernetes manifests |

### 🎙️ Interview Answer: "How do you manage Terraform state?"
> *"In production, we never store the state file locally or in Git. We use a remote backend — the state file lives in an S3 bucket for shared access, and a DynamoDB table provides state locking so two engineers can't run `terraform apply` simultaneously and corrupt the infrastructure."*

### 🎙️ Interview Answer: "What is State Drift?"
> *"State drift happens when someone manually modifies cloud resources through the console instead of Terraform. The state file no longer matches reality. You can detect this with `terraform plan` — it will show unexpected changes. The fix is to either import the manual change into Terraform or revert it."*

# 🗂️ Day 22: Project Management Tools for DevOps

**Goal:** Understand the non-technical workflows every DevOps engineer faces in their first week.

---

## 🔵 Agile vs Waterfall

| Method | How It Works | Problem |
|---|---|---|
| **Waterfall** (Old) | Design → Code → Test entire app in one 4–5 month cycle | Bugs found at the end = expensive to fix |
| **Agile** (Modern) | Break work into 2–3 week **Sprints**, deliver incrementally | Bugs caught early, feedback is immediate |

> 🎯 **DevOps follows Agile** — automated pipelines enable frequent, small deliveries.

---

## 🔵 Jira — The Industry Standard Tracker

> Jira implements Agile at the team level.

| Level | Who Uses It | For What |
|---|---|---|
| **Executive** | Management | Track P1 (critical) bugs across the org |
| **Team** | Developers, DevOps | See Sprint stories, manage backlog |

| Term | Meaning | Example |
|---|---|---|
| **Epic** | Large feature/goal | "Enable 15-minute delivery" |
| **Story** | Task broken from an Epic | "Create Kubernetes Cluster" |
| **Sprint** | 2–3 week work cycle | Team commits to 5 stories |
| **Backlog** | Queue of pending tasks | Stories waiting for next sprint |

> 💡 **Tip:** Create a free Atlassian account to practice Jira before your first day.

---

## 🔵 Confluence & SharePoint — The Knowledge Library

> Code lives in Git. Knowledge lives in Confluence.

| Tool | Company | Purpose |
|---|---|---|
| **Confluence** (Atlassian) | Enterprise teams | Internal docs, runbooks, architecture decisions |
| **SharePoint** (Microsoft) | Microsoft shops | Same purpose — knowledge base |
| **Read the Docs** | Open source | Public documentation hosted alongside GitHub |

**Why it matters:** If a senior engineer leaves, their knowledge stays documented — new hires can onboard without starting from zero.

---

## 🔵 ServiceNow — The Firefighter's Tool

> Large organizations (banks, enterprises) use ServiceNow for two processes:

### 🔥 Incident Management (Reacting to problems)
```
CloudWatch detects crash
      ↓
Alert fires
      ↓
ServiceNow creates Incident Ticket automatically
      ↓
Assigned to on-call engineer to fix immediately
```

### 🛠️ Change Management (Deploying to production)
```
Bug fixed → want to deploy to Production
      ↓
Open a Change Request in ServiceNow
      ↓
Document: downtime window, rollback plan, approvals
      ↓
Approved → deploy
```

> ⚠️ **You cannot just push code to a live bank server.** Change Management ensures accountability, audit trails, and rollback plans.

---

## 🔵 Open Source Project Management

| Tool | Used When |
|---|---|
| **GitHub Projects** | Open source — free, integrated with repo |
| **Azure Boards** | Microsoft ecosystem |

### 🎙️ Interview Answer: "How do you track your DevOps work?"
> *"We use Jira for sprint planning and backlog management. Epics represent large goals, broken into Stories that are completed sprint by sprint. For documentation, I use Confluence to write runbooks, deployment guides, and architecture decisions. In production environments, any deployment to prod goes through a ServiceNow Change Request with documented rollback plans and manager approval."*

# 📦 Day 23: Introduction to Containers

**Goal:** Understand why containers exist, how they differ from VMs, and the Docker lifecycle.

---

## 🔵 The Evolution of Hosting

```
Physical Servers → Virtual Machines → Containers
(wasteful)          (better, but heavy)  (efficient & portable)
```

| Era | Technology | Problem |
|---|---|---|
| **Physical Servers** | Bare metal servers | 100GB RAM, app uses 10GB → 90GB wasted |
| **Virtual Machines** | Hypervisors | Better, but each VM has a full OS — still heavy |
| **Containers** | Container Engine | Share host kernel — tiny, fast, portable |

---

## 🔵 VM vs Container (The Interview Comparison)

| Feature | Virtual Machine | Container |
|---|---|---|
| **OS** | Full Guest OS (kernel + libs + apps) | Minimal — only app + required libraries |
| **Size** | 1–3 GB | 100–500 MB |
| **Isolation** | High — completely separate OS | Logical — shares host kernel |
| **Speed** | Slower to start | Starts in milliseconds |
| **Runs on** | Hypervisor (VMware, Xen) | Container Engine (Docker) |

> 💡 **Modern best practice:** Run containers *inside* VMs (EC2 instances) — get security of VMs + efficiency of containers.

---

## 🔵 The Docker Lifecycle

```
Dockerfile → docker build → Docker Image → docker run → Docker Container
(instructions)               (read-only template)          (live running app)
```

| Step | What It Is |
|---|---|
| **Dockerfile** | Text file with build instructions |
| **Docker Image** | Read-only snapshot (like a class in OOP) |
| **Docker Container** | Running instance of an image (like an object) |

---

## 🔵 Buildah — The Alternative to Docker

| | Docker | Buildah |
|---|---|---|
| **Architecture** | Relies on Docker Engine (daemon) | Daemonless — no central engine |
| **Problem** | If engine crashes → ALL containers stop | No single point of failure |
| **Use Case** | Standard container workflows | CI/CD automation, used with Podman & Skopeo |

### 🎙️ Interview Answer: "VM vs Container?"
> *"A VM runs a full operating system on top of a hypervisor — it's isolated but heavy, typically 1–3GB. A container shares the host OS kernel and only packages the app and its dependencies, making it 100–500MB. Containers start in milliseconds vs minutes for VMs. In practice, we often run containers inside EC2 instances to get the management benefits of VMs with the efficiency of containers."*

# 🐳 Day 24: Docker Zero to Hero — Part 1

**Goal:** Understand Docker architecture, install it, and build your first container.

---

## 🔵 Why Containers Are Lightweight (Deep Dive)

```
Ubuntu VM Image  = ~2.3 GB  (full OS: kernel + libs + networking)
Ubuntu Docker Image = ~28 MB (kernel stripped — shared from host)
```

**Result:** Run 30–40 containers on a machine that might only support 1–2 VMs.

---

## 🔵 Docker Architecture

```
┌────────────────────────────────────────────────┐
│  Developer types: docker build / docker run     │
│              Docker Client (CLI)                │
└────────────────────┬───────────────────────────┘
                     │ API call
┌────────────────────▼───────────────────────────┐
│              Docker Daemon                      │
│  (heart of Docker — manages all containers)    │
│  ⚠️ If Daemon crashes → all containers stop    │
└────────────────────┬───────────────────────────┘
                     │ pull/push
┌────────────────────▼───────────────────────────┐
│           Docker Registry (Docker Hub)          │
│  Stores images — like GitHub but for containers │
└────────────────────────────────────────────────┘
```

| Component | What It Is |
|---|---|
| **Docker Client (CLI)** | Where you type commands — sends requests to Daemon |
| **Docker Daemon** | Background process that manages containers |
| **Docker Registry** | Storage for images (Docker Hub = public, ECR = AWS private) |

> 📌 **Interview note:** GitHub = source code storage | Docker Hub = container image storage

---

## 🔵 Installation & Common Error Fix

```bash
# Install Docker on Ubuntu EC2
sudo apt update
sudo apt install docker.io

# Fix "Permission Denied" error
sudo usermod -aG docker $USER
# Then log out and log back in
```

**Why the error happens:** Docker Daemon runs as root. Normal user (`ubuntu`) can't access it by default. Adding user to `docker` group fixes this.

---

## 🔵 Writing a Dockerfile (Python Hello World)

```dockerfile
FROM ubuntu:latest         # Base OS image
WORKDIR /app               # Set working directory inside container
COPY . .                   # Copy code from laptop into container
RUN apt-get install -y python3   # Install dependencies
CMD ["python3", "app.py"]  # Command to run when container starts
```

| Instruction | Purpose |
|---|---|
| `FROM` | Defines the base image (starting point) |
| `WORKDIR` | Sets the directory inside the container |
| `COPY` | Copies files from host into the container |
| `RUN` | Executes commands during image build |
| `CMD` | Command that runs when container starts |

---

## 🔵 Build, Run & Share

```bash
# Build image from Dockerfile
docker build -t myapp:v1 .

# Run the container
docker run myapp:v1

# Share on Docker Hub
docker login
docker push username/myapp:v1

# Pull on any other machine
docker pull username/myapp:v1
```

### 🎙️ Interview Answer: "Explain Docker architecture"
> *"Docker uses a client-server architecture. The Docker client CLI is where I type commands — it sends API requests to the Docker Daemon, which is the background process that actually manages containers. Images are stored in a registry like Docker Hub. The key limitation is that the Daemon is a single point of failure — if it crashes, all containers on that host go down."*

# 🐳 Day 25: Docker Containerization for Django

**Goal:** Containerize a real-world Python Django web app and expose it to the internet.

---

## 🔵 Why Containerize? ("Works on My Machine" — Solved)

Without containers:
- Works on developer's Mac ✅
- Fails on QA's Windows ❌
- Fails on production Linux ❌

With containers:
- App + all dependencies bundled together
- Runs **identically everywhere** — Mac, Windows, Linux, cloud

---

## 🔵 Do DevOps Engineers Need to Code?

> **No — but you must understand the app flow.**

To write a Dockerfile, you need to know:
1. Which language the app uses (Python)
2. Where dependencies are listed (`requirements.txt`)
3. How to start the app (`manage.py runserver`)

---

## 🔵 Dockerfile for Django

```dockerfile
FROM ubuntu                          # Base OS
WORKDIR /app                         # Working directory
COPY requirements.txt .              # Copy dependency list first
RUN pip install -r requirements.txt  # Install Django and libs
COPY . .                             # Copy all source code
CMD ["python3", "manage.py", "runserver", "0.0.0.0:8000"]
```

> 💡 **Why `COPY requirements.txt` before `COPY . .`?**
> Docker builds in layers. Copying requirements separately means Docker can cache the pip install step — if only your code changes (not requirements), the install layer is reused and build is faster.

---

## 🔵 ENTRYPOINT vs CMD — Major Interview Topic

| | ENTRYPOINT | CMD |
|---|---|---|
| **Can be overridden?** | ❌ Not easily | ✅ Yes, at runtime |
| **What to put here** | The main executable (`python3`) | The arguments (`manage.py runserver`) |
| **Use case** | Lock in the runtime — prevent running as wrong language | Allow flexible arguments |

```dockerfile
ENTRYPOINT ["python3"]                        # Locked — always use python3
CMD ["manage.py", "runserver", "0.0.0.0:8000"] # Can override at runtime
```

```bash
# Override CMD at runtime (without rebuilding image):
docker run myapp manage.py migrate
docker run myapp manage.py shell
```

### 🎙️ Interview Answer: "ENTRYPOINT vs CMD?"
> *"Both define how a container starts, but CMD arguments can be overridden at runtime while ENTRYPOINT cannot be easily overridden. I use ENTRYPOINT for the fixed executable — like `python3` — so users can't accidentally run it as a different runtime. I use CMD for arguments like `manage.py runserver` so operators can pass different commands without rebuilding the image."*

---

## 🔵 Port Mapping — Accessing the App

**Problem:** App runs inside container on port 8000. Your browser can't reach it.

**Fix:** Map container port to host port:

```bash
docker run -p 8000:8000 myapp:v1
#           ^host ^container
```

```
Browser → EC2 Public IP:8000 → Host Port 8000 → Container Port 8000 → Django App
```

**Still can't access?** Check AWS Security Group:
```
EC2 → Security Groups → Inbound Rules → Add:
  Type: Custom TCP | Port: 8000 | Source: 0.0.0.0/0
```

### 🎙️ Interview Answer: "How do you expose a containerized app?"
> *"I use port mapping with `docker run -p <host-port>:<container-port>`. This binds the container's internal port to a port on the host machine. On AWS, I also need to open the port in the EC2 Security Group's Inbound Rules — AWS blocks all traffic by default except SSH on port 22."*
